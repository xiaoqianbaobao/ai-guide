# 知识库、Agent 上下文与个人记忆如何分工

> 最后核验：2026-11-15。本文是基于研究形成的架构建议，具体产品能力应按部署版本核对。

Agent 需要长期可用的知识，也需要随任务变化的上下文和个人偏好。这些信息生命周期不同：把它们全放进一份自动更新的记忆，会使来源、权限和纠错责任变得模糊。

## 三类信息，各有边界

| 类型 | 例子 | 权威来源 | 主要使用方式 |
| --- | --- | --- | --- |
| 可审阅知识 | 产品规则、架构决策、经过核验的研究 | Wiki 或 Git 中可追踪版本的内容 | 人审阅、修订，Agent 检索并引用 |
| 运行时上下文 | 当前任务、检索片段、工具结果、交接状态 | 原始系统和当前任务记录 | 按需组装，任务结束后按策略保留 |
| 私有个人记忆 | 个人偏好、授权范围、跨任务习惯 | 用户可管理的私有存储 | 在获得授权且与任务相关时检索 |

例如，团队架构决策应有可审阅的原文和版本；Agent 的摘要可以帮助检索，却不能自动覆盖原文。个人偏好也不应因任务中被使用就自动进入公开知识库。

## 一类知识只有一个权威写入面

研究型场景可以使用 Git/Wiki 作为领域知识的权威副本，OpenViking 等上下文系统提供运行时检索和私有记忆。检索索引可以重建；Agent 发现新信息时先提出带证据的修改建议，再经适当审核写入权威来源，随后更新索引。

流程可以从小处实现：原始资料 → 带来源的草稿 → 人工核验 → Git/Wiki 版本 → 可重建索引 → 按权限检索。每条结论保留来源、采集时间和版本；来源变化时标记待复核。不要把双向自动同步当作默认方案，否则循环更新、冲突和事实分叉难以追踪。

## 何时写入，如何撤回

写入前判断信息是否可验证、是否长期有价值、是否包含敏感内容，以及谁有权看到。事实与推测分开存储，过期的信息标记失效而不是悄悄覆盖。撤回时不仅要修改权威来源，还要让索引和缓存失效；审计记录按组织的隐私与保留策略处理。

## 一个最小验证方案

选择一个资料密集且持续更新的小项目：把已核验资料放入 Wiki/Git，建立只读索引；保留私有记忆的独立权限；准备十个有出处的检索问题和几个权限边界问题。比较回答正确性、引用准确性、过期信息召回及未授权访问情况。该方案是待验证的设计，不是已完成的性能结论。

## 从一个冲突案例理解“权威”

假设团队曾在 Wiki 写明“外部数据保留 30 天”。一次讨论中有人提议改为 90 天，Agent 将讨论摘要写入长期记忆，但正式规则还没有审批。三周后，检索系统同时召回两条记录：Wiki 说 30 天，记忆说 90 天。如果只按语义相似度挑选最相关的段落，Agent 可能把提议误当成已生效规则。

解决办法不是让模型“更聪明地猜”，而是给不同内容定义地位：Wiki 中有版本的已批准规则是权威事实；讨论摘要标注为提议、作者、日期与审批状态；个人记忆保存某人的偏好，不参与覆盖组织规则。冲突出现时应返回来源和状态，必要时由有权的人决定。

### 四个容易混在一起的概念

- **原始资料**：会议记录、邮件或网页，是证据，但可能错误或过期。
- **整理后的知识**：经过归纳和审核的解释，可能引用多份资料；每次变更应能追溯到来源。
- **检索索引**：从权威内容派生的切片、向量或关键词索引；为效率而存在，可以重建，不应成为无来源的新事实。
- **运行时上下文**：为当前任务临时拼装的内容，包括用户授权、检索结果与工具反馈；任务结束后按照数据策略清理或归档。

个人记忆则按用户及授权域隔离。某个系统可以同时承载多类数据，但逻辑上的权限与生命周期不能因此消失。

## 一条结论从资料到答案，经历了什么

以一份架构决策为例，先将来源材料归档，记录 URL 或文件版本、采集时间、作者、许可与访问范围。整理时给结论标明支持证据和适用条件；存在冲突则保留冲突，而不是把互相矛盾的资料合并成一条模糊结论。审阅通过后进入 Git/Wiki，并产生内容版本。

索引程序读取该版本，按标题与语义切分，保存 `source_id`、`revision`、权限标签和切片位置。用户提问时，检索先根据身份筛选可见范围，再排序并返回片段；生成答案时保留来源和版本。若系统先对全库检索、再把无权限的内容交给模型过滤，敏感信息已越过了授权边界。

下面是一个示意记录：

```yaml
claim_id: retention-policy
status: approved
statement: 外部数据保留 30 天
source: wiki/policies/retention.md
source_revision: git-9f2c1a
valid_from: 2026-01-01
access: internal
reviewed_at: 2026-11-15
```

此结构并非 OpenViking 或某个 Wiki 的真实 API。`reviewed_at` 说明何时核验，`valid_from` 说明何时生效：两者解决不同问题。如果来源日期、适用范围或状态不明，就应标为待核验，而不是填一个看起来合理的值。

## 更新、撤回和索引同步的竞态

假设 Wiki 的权限从“全员可读”改为“项目组可读”，旧向量索引仍带着旧权限，或者缓存尚未过期，那么即便原文已保护，旧副本仍可能被召回。安全设计要让检索时的授权判断以当前可信权限为准，权限变更主动失效相关索引和缓存；异步同步期间的行为也要定义清楚，高风险内容宜默认拒绝而不是继续使用旧授权。

内容被更正时，索引更新也不是只有“新增向量”：旧切片需要删除或标为失效，答案缓存需要失效；如果索引更新失败，应有可监控的队列、重试与对账。删除请求还要覆盖可访问的副本和备份策略，不能把“主表已删除”当作全部完成。

## 怎样评估这套设计

建立一组带身份与时间的测试问题，例如：同一问题由不同成员提问是否只返回各自可读的内容；新版本覆盖旧版本后是否还会引用旧规则；用户的私人偏好是否泄露给团队；两份资料相互冲突时是否说明冲突。分别统计检索命中、引用可核验、过期召回、越权召回以及更新到生效的时间。

检索质量差时，要区分原因：资料本身不存在、切片切断了上下文、权限过滤过严、排序错误，或生成阶段误用了正确资料。不要只靠调整 embedding 模型解决所有问题。

## 动手试一试：过期索引为什么不能当权限依据

以下 Python 3 示例只模拟读取阶段的规则，不是完整的授权系统。它刻意让索引权限过期，观察读取时重新核验当前权限如何阻止旧副本泄露。

```python
# 索引曾经记录所有人可读；原文权限后来收紧。
index = {"doc-1": {"snippet": "保留期为 30 天", "cached_acl": {"alice", "bob"}}}
current_acl = {"doc-1": {"alice"}}

def retrieve_for(user, doc_id):
    # 真实系统中权限应由可信的授权服务提供，并处理不可用和缓存失效。
    if user not in current_acl.get(doc_id, set()):
        return None
    return index[doc_id]["snippet"]

print("Alice:", retrieve_for("alice", "doc-1"))
print("Bob:", retrieve_for("bob", "doc-1"))
assert retrieve_for("bob", "doc-1") is None
```

如果把检查条件错误地换成 `index[doc_id]["cached_acl"]`，Bob 会重新看到片段。实践中还要确保排序、缓存、引用和日志不会先泄露受限内容，并为授权服务不可用定义安全的失败行为。
