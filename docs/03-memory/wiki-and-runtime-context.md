# 知识库、Agent 上下文与个人记忆如何分工

> 最后核验：2026-11-15。本文是基于研究形成的架构建议，具体产品能力应按部署版本核对。

Agent 需要长期可用的知识，也需要随任务变化的上下文和个人偏好。这些信息生命周期不同：把它们全放进一份自动更新的记忆，会使来源、权限和纠错责任变得模糊。

## 三类信息，各有边界

| 类型 | 例子 | 权威来源 | 主要使用方式 |
| --- | --- | --- | --- |
| 可审阅知识 | 产品规则、架构决策、经过核验的研究 | Wiki 或 Git 中可追踪版本的内容 | 人审阅、修订，Agent 检索并引用 |
| 运行时上下文 | 当前任务、检索片段、工具结果、交接状态 | 原始系统和当前任务记录 | 按需组装，任务结束后按策略保留 |
| 私有个人记忆 | 个人偏好、授权范围、跨任务习惯 | 用户可管理的私有存储 | 在获得授权且与任务相关时检索 |

例如，团队架构决策应有可审阅的原文和版本；Agent 的摘要可以帮助检索，却不能自动覆盖原文。个人偏好也不应因任务中被使用就自动进入公开知识库。

## 一类知识只有一个权威写入面

研究型场景可以使用 Git/Wiki 作为领域知识的权威副本，OpenViking 等上下文系统提供运行时检索和私有记忆。检索索引可以重建；Agent 发现新信息时先提出带证据的修改建议，再经适当审核写入权威来源，随后更新索引。

流程可以从小处实现：原始资料 → 带来源的草稿 → 人工核验 → Git/Wiki 版本 → 可重建索引 → 按权限检索。每条结论保留来源、采集时间和版本；来源变化时标记待复核。不要把双向自动同步当作默认方案，否则循环更新、冲突和事实分叉难以追踪。

## 何时写入，如何撤回

写入前判断信息是否可验证、是否长期有价值、是否包含敏感内容，以及谁有权看到。事实与推测分开存储，过期的信息标记失效而不是悄悄覆盖。撤回时不仅要修改权威来源，还要让索引和缓存失效；审计记录按组织的隐私与保留策略处理。

## 一个最小验证方案

选择一个资料密集且持续更新的小项目：把已核验资料放入 Wiki/Git，建立只读索引；保留私有记忆的独立权限；准备十个有出处的检索问题和几个权限边界问题。比较回答正确性、引用准确性、过期信息召回及未授权访问情况。该方案是待验证的设计，不是已完成的性能结论。
