## Chatbot 和 Agent 的差别是什么

关键差别不是界面，而是闭环。

聊天机器人通常只负责接收输入并返回回答，Agent 则会进一步：

- 读取环境
- 选择动作
- 调用工具
- 根据结果继续推理

只要系统开始依赖“感知 -> 推理 -> 行动 -> 反馈”这个循环，它就已经进入 Agent 的问题域。

## LLM 在其中扮演什么角色

LLM 更像推理引擎，而不是 Agent 本身。

真正的 Agent 是下面这些部分的组合：

- 模型：负责理解和推理
- 工具：负责访问外部能力
- 状态：负责保留上下文和任务进度
- 控制逻辑：负责循环、停止、重试和异常处理

如果只有模型，没有这些外围结构，那通常还只是一次增强问答，而不是完整 Agent。

## 一个最小闭环长什么样

最简单的 Agent 也通常包含下面四步：

1. 接收任务
2. 判断当前需要什么信息或动作
3. 调用工具或继续推理
4. 根据返回结果更新下一步

这和传统函数调用的最大差别在于：它不是一次性完成，而是允许系统在过程中重新判断和调整。

## 为什么这件事重要

一旦你接受这个定义，就会自然理解后面的模块为什么不是“附加主题”，而是 Agent 的组成部分：

- `Tool Use` 解决行动能力
- `Context Engineering` 解决模型在每一步看到了什么
- `Memory` 解决跨轮状态和长期信息保留
- `Eval` 解决不确定系统的可控性

## 常见误解

### 误解一：只要能自动回答很多问题，就是 Agent

不一定。

如果系统只是根据输入返回一段文本，没有感知环境、没有外部行动、没有闭环反馈，那它更接近一个增强聊天系统。

### 误解二：Agent 一定要非常复杂

也不一定。

一个最小 Agent 完全可以很简单。关键不在于模块多少，而在于它是否真的具备闭环。

### 误解三：Agent 的核心是“更强的模型”

模型强当然有帮助，但很多时候系统表现差，问题并不在模型，而在：

- 工具描述不清
- 上下文混乱
- 状态管理失真
- 没有停止和验证机制

## 一个最小示例

下面这段代码不是完整 Agent，只是帮助你看清闭环结构。

```python
task = "读取日志并总结错误原因"

state = {
    "task": task,
    "observations": [],
    "done": False
}

while not state["done"]:
    # 这里原本应由模型决定下一步动作
    action = "read_log"

    if action == "read_log":
        observation = "发现端口已被占用"
        state["observations"].append(observation)
        state["done"] = True

print(state)
```

这段代码的重点不在实现质量，而在结构：

- 有任务
- 有状态
- 有动作
- 有反馈
- 有停止条件

这就是 Agent 设计的起点。

## 和工作流的区别

很多人第一次接触 Agent 时，会把它和工作流混在一起。

一个更简单的区分方法是：

- 工作流：步骤大多由人提前写死
- Agent：步骤在运行中由系统动态决定

现实系统里，两者经常会混合存在，但理解这个差别有助于你判断何时真的需要 Agent。
