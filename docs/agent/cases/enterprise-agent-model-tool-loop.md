# 给企业助手接入模型：一条有边界的只读工具调用链

[本地企业助手](./enterprise-agent-local-lab)已经能查规则、审核草稿和模拟提交，但它用的是字面匹配，不会让模型决定何时调用工具。本课给它增加一个**可选的只读模型工具循环**：模型可以建议查询关键词，服务端根据当前身份查询演示文档，再把结果交回模型。

这一步仍是教学原型：真实模型调用需要学习者自行配置，本文的离线测试使用模拟模型；当前没有真实身份认证、生成答案的事实校验或生产部署能力。模型**没有创建、批准或提交工单的工具**。

## 1. 一次工具调用经过哪些边界

```text
用户问题
  → 模型建议 lookup_policy(query)
  → 程序校验工具名称和参数
  → 服务端用可信身份过滤租户，再查询演示文档
  → 工具结果作为数据返回模型
  → 生成待人工核对的回答，来源由服务端记录
```

模型可以提出要查什么，但不能决定自己属于哪个租户。`lookup_policy` 的参数只有 `query`，如果模型额外提出 `tenant` 或请求 `create_ticket`，程序会拒绝。这个约束由应用程序执行，不能只靠提示词。

返回给模型的文档仍是低信任数据。提示词要求模型不要把它当指令，但这不是充分的提示注入防御；实际系统还需要限制可访问资料、隔离工具权限、监控以及对抗测试。参见 [Agent 安全边界](../../02-agent-core/agent-security-boundaries)。

## 2. 先离线运行测试

不安装模型 SDK、不提供密钥，也不访问外网，先在仓库根目录运行：

```bash
cd examples/enterprise-agent-lab
python3 -m unittest test_agent_loop -v
```

7 条测试使用模拟模型或模拟 SDK，覆盖：查询结果按 `call_id` 返回、来源由服务端提供、无证据时丢弃模型编造的回答、禁止模型自选租户或写入工具、无效参数、轮次上限及缺少联网开关时不创建提供方客户端。它们验证应用逻辑，**不证明真实模型或真实 API 请求已经跑通**。

如果已经安装官方 `openai` SDK，还可以运行 `python3 -m unittest test_sdk_contract -v`：它使用 SDK 和本地模拟 HTTP 响应，验证两轮请求的序列化与工具结果格式，不连接外网。未安装 SDK 时该测试会跳过；本文用 SDK 2.44.0 完成过模拟测试，不代表不同版本和真实服务一定兼容。

完整代码见 [agent_loop.py](https://github.com/xiaoqianbaobao/ai-guide/blob/main/examples/enterprise-agent-lab/agent_loop.py)。关键的服务端调用是：

```python
# identity 由可信调用方提供，不来自模型生成的工具参数。
result = service.ask(identity, arguments["query"])
history.append({"type": "function_call_output", "call_id": call["call_id"],
                "output": json.dumps(result, ensure_ascii=False)})
```

这里的“可信调用方”在本地示例里仍然只是写死的演示身份。生产系统需要真正的身份认证、租户与文档级鉴权；不能把这个演示身份搬到公网。

## 3. 可选：自行连接真实模型

此步骤会产生外部网络请求，并可能产生 API 费用；只使用虚构问题。示例每次创建独立的临时演示数据库，不读取或发送你此前本地实验室数据库中的记录。**你的问题以及模型选中的授权演示文档片段会发送给 API 提供方。** `store=False` 是请求设置，不应被理解为提供方完全没有日志或其他数据保留；以提供方当前政策和组织协议为准。

1. 在 `examples/enterprise-agent-lab` 创建并激活 Python 虚拟环境，安装官方 `openai` Python SDK。运行前检查 SDK、模型可用性和计费信息；它们可能随时间变化。
2. 通过安全方式在当前进程环境配置 `OPENAI_API_KEY`，并设置 `OPENAI_MODEL` 为你有权使用、支持 Responses 和函数调用的模型。不要把真实密钥写入源码、截图或仓库。
3. 确认配置的 API 服务地址与组织策略后，显式运行：

```bash
python3 agent_loop.py --allow-network --question '退款政策是什么？'
```

若未提供显式开关、模型名或密钥，程序会在发请求前退出。示例限制每次最多 3 轮模型调用、单次输出上限 400 token、单次网络超时 20 秒且不自动重试；这些是演示限额，**不是费用上限或完整预算控制**。模型、输入、供应商价格与失败情况会影响实际费用。若依赖、网络、账户或模型不满足要求，命令可能失败；本课程没有提供已验证的真实 API 运行结果。

## 4. 工具结果、最终回答与可验证性

服务端把查询得到的来源 ID 单独收集，最终结果中的 `sources` 不由模型自行编造；没有来源时，程序直接返回“无法确认”，不会展示模型声称的答案。

但这还不等于已经验证回答：有来源只说明至少一次查询找到授权材料，**不保证模型的每句话都被来源支持**。因此示例把有来源的结果标记为 `needs_review`。实际应用还要逐条检查引用与结论、检测版本撤回、记录评估数据，并规定人工复核与失败升级路径。模型可以没有调用工具就给出答案；本例在这种情况下会拒绝展示其结论。

## 5. 如何测试失败而不是只看成功

| 情况 | 本例的行为 | 后续需要补什么 |
| --- | --- | --- |
| 模型请求不存在的写工具 | 拒绝，停止循环 | 服务端工具网关、审计和细粒度策略 |
| 模型追加 `tenant` 参数 | 参数校验失败 | 真实身份绑定与文档级授权 |
| 查询未命中但模型声称知道 | 返回资料不足 | 检索质量、拒答质量和人工升级评估 |
| 模型反复请求工具 | 达到轮次上限后停止 | 全局时间、token、费用与并发预算 |
| 查询命中但回答扭曲来源 | 标记待审核，程序本身不保证发现 | 引用逐项核验、对抗测试和人工抽查 |

不要将本例直接对接企业资料，也不要把模型生成的文本自动传给工单提交接口。后续如需写操作，先回到[审批与幂等实验](./ticket-approval-and-retry)，设计明确的用户授权、可信审核和跨服务对账。

## 6. 动手练习

1. 在模拟模型测试里添加一个未知工具名，确认它不会触发任何数据库写入。
2. 让模拟模型先查询“薪酬”，再声称退款规则；观察客服身份得不到人事文档，最终不能输出无来源结论。
3. 为 `needs_review` 设计一个人工核对清单，区分“来源存在”和“来源支持每个关键结论”。
4. 画出真实模型、检索服务、身份系统和工单系统之间的数据流，明确哪些内容可能发送给外部提供方。
