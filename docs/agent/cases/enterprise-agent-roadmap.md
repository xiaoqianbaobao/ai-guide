# 企业级 Agent 实战路线：从知识助手到可治理工作流

> 状态：部分阶段已有可运行的本地教学原型和测试；真实身份、生产系统集成及部署验收仍未完成。独立练习不等于已经接入同一个企业应用。

可以先动手完成 [企业知识助手第一刀](./knowledge-assistant-first-slice)：用 Python 运行一个带授权过滤、引用与拒答的只读教学原型。也可以直接运行[本地企业助手闭环](./enterprise-agent-local-lab)，体验查询、草稿、审批与模拟工单的 HTTP 流程；该示例仍没有真实认证、模型或生产集成。

## 为什么选择一个连续场景

企业级 Agent 不是把模型接上数据库就完成了。一个有用的系统必须回答：谁可以看哪些信息？引用能否追溯？工具失败如何恢复？错误执行后怎么止损？新版本上线会不会让旧任务退化？这些问题分散在不同文章里，读者很难从头拼出一个可运行系统。

本系列以**企业内部知识与工单助手**为教学场景：员工提问，助手检索自己有权访问的文档并给出引用；当资料不足时，它可以准备一份工单草稿，供有权限的人审核后提交。课程先使用虚构数据和本地模拟服务，再逐步接真实身份和业务系统。

这个选择是为了覆盖检索、授权、写入、审批与评估，不意味着所有企业都适合直接部署这个示例。真实部署须按组织身份、数据分级和业务流程重新设计。

## 最终完成的用户旅程

1. 用户以可信身份登录，提出问题；服务端确定其租户和角色。
2. 系统只检索该身份当前有权读取的文档；答案引用来源及版本，证据不足时明确说明。
3. 用户要求创建工单时，Agent 生成待审草稿，由服务端校验目标、内容和权限。
4. 审批人看到具体内容与目标；批准后执行器以稳定操作 ID 提交，并对超时进行查询或对账。
5. 管理员可追踪脱敏后的任务、工具调用、审批与错误，并通过回归集评估更新。

这些是**目标行为**，并非声称现有站点已经实现。即使示例实现完成，也需要实际环境的安全评审、容量与恢复测试，才可决定是否上线。

## 分阶段交付与验收

| 阶段 | 需要交付 | 读者能亲自验证的完成条件 |
| --- | --- | --- |
| 0. 定义任务和边界 | 虚构企业案例、用户角色、数据分级、架构和威胁模型 | 说清允许查询与禁止外发的范围，准备可复现测试数据 |
| 1. 端到端最小系统 | 前端、后端、模型适配接口、模拟知识源和本地启动文档 | 使用测试数据提问并获得带出处的回答；无证据时拒绝编造 |
| 2. 知识接入与检索 | 文档导入、切分、索引、引用版本及更新流程 | 修改或撤回文档后，检索能处理旧索引与缓存失效 |
| 3. 身份与权限 | 可信身份上下文、租户隔离、工具服务端鉴权 | 两个租户的用户不能从检索、缓存、日志或工具结果取得彼此数据 |
| 4. 受控工具与审批 | 工单草稿、审批记录、模拟工单服务、幂等与对账 | 审批前无写入；重复提交不产生重复工单；审批目标变化需重新确认 |
| 5. 状态与恢复 | 任务状态、检查点、超时、重试和可恢复记录 | 在写入前、响应丢失后、状态持久化前注入故障并验证恢复路径 |
| 6. 评估与观测 | 脱敏轨迹、任务集、确定性检查、人工抽样与告警 | 能重跑正常、越权、提示注入、证据不足和依赖故障用例，并比较版本 |
| 7. 部署演练 | 部署配置、密钥管理、备份、回滚、运维手册和成本预算 | 在隔离测试环境完成部署、故障演练与回滚，并记录环境和限制 |

每阶段必须说明依赖版本和运行环境，提供命令与预期输出；没有真实运行的代码标记为伪代码。示例不能放真实客户数据或密钥。对业务有副作用的功能默认连接模拟服务。

## 系统边界和关键选择

**知识检索**：索引是源文档的可重建副本，而不是事实权威。检索与缓存都需要执行授权检查；答案中的引用应能映射到可访问的来源版本。先阅读 [知识库与运行时上下文](../../03-memory/wiki-and-runtime-context)，再通过[企业知识的权限与撤回](../../09-data-governance/knowledge-access-lifecycle)动手检查租户隔离、版本更新和撤回。

**工具执行**：模型只提出调用意图。服务端按用户、租户、工具、目标和数据权限决定是否执行；外部内容不能授予新权限。参见 [Agent 安全边界](../../02-agent-core/agent-security-boundaries)。

**执行状态**：对外部副作用保留操作 ID、目标摘要和状态；未知结果先对账再决定是否重试。下游不支持幂等或查询时，需要人工核对或补偿。参见 [Agent 工程闭环](../../05-tools-frameworks/agent-engineering-loop)。

**质量和风险**：同时检查结果正确性、授权边界、执行轨迹、成本与延迟。记忆、模型或提示词变化后必须重跑关键任务；不可将一次演示当作上线依据。参见 [线上评估与回归](../../06-eval-evolution/production-evaluation-loop)。

## 最小回归样例：已有覆盖与剩余缺口

下表列出**教学原型中的具体测试**，不代表真实企业环境通过验收。演示身份是固定身份，不是真实登录；不同目录的练习也尚未全部接成一个端到端系统。

| 场景 | 可运行的证据 | 仍需补充 |
| --- | --- | --- |
| 正常问答与租户过滤 | `test_knowledge_is_filtered_by_tenant`：退款命中来源；客服查询人事资料得到资料不足 | 真实身份、文档级权限及缓存、日志等全部数据通道的隔离 |
| 资料不足 | `test_no_evidence_does_not_return_model_claim`：模拟模型声称答案时，缺少来源仍拒答 | 对真实模型和多种无答案任务评估拒答质量 |
| 注入内容要求写操作 | `test_injected_document_cannot_authorize_write_tool`：模拟模型请求未开放的写工具，被拒绝 | 不能由此推断不会泄露或污染回答；同一测试文件还演示回答仍可能被污染 |
| 批准与重复提交 | `test_approval_and_replay_do_not_duplicate_ticket`：未批准不能提交，相同操作重试只创建一条模拟工单 | 接入真实审批、调用主体、目标系统及可审计授权 |
| 草稿修改或批准过期 | `test_modified_draft_cannot_use_old_approval`、`test_expiry_rejects_new_write_but_not_replay_of_completed_write` | 跨服务部署时验证审批与实际操作参数的绑定 |
| 外部提交准备与取消 | `test_external_prepare`：固定已批准版本和操作 ID；未发送的意图可由同租户审核人取消，旧 ID 不能复用 | 无真实身份或对外 HTTP 入口；重放不会延长审批，未知状态不可当作未发送取消 |
| 下游写入后响应丢失 | `test_external_delivery`：已批准意图接入本机模拟 HTTP 服务，响应丢失后按同一 ID 对账 | 仅领取资格时检查批准时效，网络发送时可能已过期；真实下游合同、身份、租约和人工对账仍需实现 |

在仓库根目录分别运行两组离线测试；每组使用独立临时数据库，不连接真实业务服务：

```bash
cd examples/enterprise-agent-lab
python3 -m unittest test_server test_agent_loop test_external_prepare test_external_delivery -v
cd ../cross-service-recovery
python3 -m unittest test_http_recovery -v
```

如果测试失败，先记录失败用例、Python 版本与错误，再判断是环境、演示代码还是假设变化；不要把某次绿色结果外推为生产安全保证。更多细节见[本地企业助手闭环](./enterprise-agent-local-lab)、[只读模型工具循环](./enterprise-agent-model-tool-loop)和[跨服务写入与对账](./cross-service-write-recovery)。

## 实施顺序

先运行已有的本地闭环和模拟下游集成，再补齐发送时授权、任务租约、人工处理未知结果等缺口。随后在隔离环境逐步引入真实身份和可控的外部依赖，每一步记录尚未覆盖的权限、运行和故障边界。不要为了展示多 Agent 而先引入多角色编排：先用任务集测出单 Agent 的瓶颈，再判断额外协调成本是否值得。参考 [OpenAI 的 Agent 评估建议](https://developers.openai.com/api/docs/guides/evaluation-best-practices)及 [Anthropic 的 Agent 评估实践](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。
