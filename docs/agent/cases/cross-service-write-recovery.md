# 工单已创建但响应丢了：跨服务写入如何恢复

用户批准了一张工单，Agent 调用工单系统后收到超时。此时界面应该显示“失败”，还是直接再创建一次？答案是：**只凭超时无法知道下游是否已经执行**。如果下游已经创建，换一个操作 ID 重试可能产生重复工单；如果根本没有创建，直接显示成功也不正确。

上一课的[本地企业助手](./enterprise-agent-local-lab)把草稿和模拟工单放在同一个 SQLite 数据库，事务能保证这个教学环境内的一致性。本课把调用方与模拟下游放到**两个独立数据库**，在下游提交后故意丢失响应或让调用方崩溃，观察恢复过程。

基础演示是单进程、单工作者的故障模拟；附加的集成测试启动独立进程，通过本机 HTTP 通信，模拟下游提交后断开连接。下游的幂等和查询行为由我们人为设定，不能代表任意第三方系统。所有业务内容均为虚构。

## 1. 三种看起来相同的超时

| 故障发生时点 | 下游是否创建 | 调用方能否仅凭超时判断 |
| --- | --- | --- |
| 请求发出前连接失败 | 没有 | 通常不能可靠推断完整过程 |
| 下游写入前中断 | 没有 | 不能 |
| 下游写入并提交后响应丢失 | 已创建 | 不能 |

真实系统的错误类型和网络协议可能提供更多线索，但跨边界的结果仍需要按下游合同核验。一个实用状态是 `unknown`：明确承认当前不知道，而不是把它误记为失败或成功。

## 2. 先记录意图，再产生副作用

本例维护两份独立记录：

```text
调用方数据库                         模拟下游数据库
operation_id + 内容 + pending  ───→  operation_id + 内容摘要 + 工单
                         响应丢失  ←── 写入已提交
unknown / 旧的 pending
       └─ 重启后按原 operation_id 查询 ─→ confirmed + 回执
```

稳定的 `operation_id` 在首次写入前就必须保存，并且同一次业务意图的重试沿用同一个 ID 和内容。示例的下游为 ID 设置唯一约束；若相同 ID 携带不同内容，就拒绝。真实 ID 应由可信服务生成并避免包含敏感信息；在这里写死的 ID 只是便于观察。

这个步骤不包含审批逻辑。真实系统在记录意图前和执行时仍要分别检查身份、租户、批准版本、有效期及撤销状态；不能把“有 operation ID”当成执行授权。

## 3. 动手运行故障演练

在仓库根目录运行，使用 Python 3.10+，不需要第三方依赖：

```bash
cd examples/cross-service-recovery
python3 recovery.py
python3 -m unittest -v
```

预期演示输出“响应丢失后: unknown”和“重启并对账后: confirmed”。10 条测试覆盖：响应丢失、下游写入后调用方崩溃、查询无结果、沿用相同 ID 重试、同 ID 不同内容的冲突，以及本机 HTTP 连接中断和服务不可用。[完整源码](https://github.com/xiaoqianbaobao/ai-guide/tree/main/examples/cross-service-recovery)在临时目录创建两个数据库，退出后自动清理。

只运行跨进程 HTTP 演练：

```bash
python3 -m unittest test_http_recovery -v
```

其中一个测试让本机下游先提交工单，再关闭连接而不发送响应；调用方记录 `unknown`，随后用相同操作 ID 查询并确认回执。另一个测试关闭服务后核验查询失败仍保留 `unknown`。HTTP 适配器把网络错误和服务端错误当成结果未知，同一 ID 的内容冲突则明确拒绝。这里的服务只监听本机，并没有连接真实工单系统。

已经保存了 `confirmed` 和回执的操作，再次执行对账时应返回已有记录。我们用独立进程测试了“先成功、再关闭下游、重启调用方”的情况：暂时查不到下游不能把已知成功降级成 `unknown`，更不能把回执清空。这里的 `confirmed` 表示该操作曾经成功创建，不表示工单此刻仍存在或业务状态没有变化；后续状态变化应由另一套同步和审计机制处理。

关键逻辑是先查询已知操作，再判断能否确认：

```python
if local_state == "confirmed":
    return saved_receipt  # 已确认的回执不因暂时无法查询而丢失
found = downstream.lookup(operation_id)
if found is None:
    mark(operation_id, "unknown")  # 查不到不自动等于没有发生
elif found["digest"] != fingerprint(local_intent):
    raise ValueError("downstream content does not match local intent")
else:
    mark(operation_id, "confirmed", found["receipt"])
```

示例中“下游查询立即可见”是模拟服务的设定。真实服务可能存在异步处理、查询延迟、幂等键过期或记录丢失；在没有可靠合同前，查不到不能简单作为安全重发的依据。

## 4. 对账、重试和人工处理如何选择

| 下游能力 | 可行方向 | 仍要核实 |
| --- | --- | --- |
| 支持按 ID 查询且查询结果可靠 | 查询已有操作并比对内容、目标和租户 | 查询一致性、权限、保存期限与异常响应 |
| 明确支持幂等写入 | 同一次意图使用相同键和相同参数重试 | 键作用域、保留期、并发与失败缓存规则 |
| 两者都不支持 | 保留未知状态并转人工对账，必要时设计补偿 | 人工能看到什么证据、谁承担业务决策 |

不要把“使用幂等键”泛化成所有系统都保证永不重复。例如 [Stripe 的幂等请求文档](https://docs.stripe.com/api/idempotent_requests)对其不同 API 版本分别说明重试与保留语义；其他服务需要查自己的文档并在目标版本测试。

## 5. 这个示例还缺什么

调用方只有一个工作者；HTTP 服务仅用于本机测试，没有认证、租户隔离、审批绑定、可靠队列、并发租约或审计查询。它不处理网络分区期间的不一致查询，也没有重试预算和人工处理界面。真实系统需要考虑至少：

- 将业务状态与待发送事件在本地事务中持久化，并处理工作者竞争、租约过期与重复投递。
- 把外部调用的权限、目标、审批版本和有效期与每次操作绑定，记录必要且受控的审计信息。
- 明确下游幂等键与查询的合同、过期时长和对账窗口；不具备可靠查询或幂等时设置人工路径。
- 在隔离环境注入失败：发送前、下游提交后、响应丢失、本地保存前、进程重启后，以及查询暂时不可用。

两个数据库不能共享一个普通 SQLite 事务。示例并没有证明通用的“恰好一次”执行；它演示的是在**特定下游保证**下，如何保存意图并恢复可验证的结果。

## 6. 练习

1. 在 `dispatch` 中启用 `crash_after_write=True`，观察重启后本地仍为 `pending`、下游已有记录；再运行 `reconcile`。
2. 在查询返回空结果后说明为什么代码保留 `unknown`；设计一个人工对账记录，需要哪些证据和责任人？
3. 将模拟下游改成不支持幂等键，验证盲目重试可能产生重复；写出禁止自动重试的策略。
4. 为操作增加租户与目标字段，先写越权和内容不匹配测试，再决定摘要与数据库约束应该包含哪些字段。
