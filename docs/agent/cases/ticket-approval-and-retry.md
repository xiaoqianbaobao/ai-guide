# Agent 写工单：审批、幂等与响应丢失

知识助手发现资料不足，准备为人工客服创建工单。模型已经生成草稿，用户也点了批准，接下来能不能直接调用 `create_ticket()`？

看似简单的写入有两个容易被忽略的问题：**批准后草稿可能被改变**；**下游已经创建成功，但响应在网络中丢失**。前者可能让用户批准 A、系统执行 B；后者如果直接使用新的请求编号重试，可能产生两张工单。

这一节在前两篇[只读原型](./knowledge-assistant-first-slice)和[回归评估](./knowledge-assistant-evaluation)的基础上，运行一个离线、虚构数据的工单服务，观察这两种情况。示例没有真实身份认证或生产审批系统，**不得直接接入真实工单服务**。

## 1. 先画出一次有风险的写入

假设草稿为“客户询问退款进度，请人工核实”，目标是 `manual-review` 队列。用户批准后，系统提交到工单服务，但接收响应之前连接断开：

```text
草稿 + 目标 → 展示给审批人 → 批准 → 提交 operation-001
                                      ↓
                               下游创建了工单
                                      ↓
                                响应丢失 / 超时
                                      ↓
                             客户端只知道结果未知
```

超时并不等于下游失败。正确做法取决于下游提供什么保证：支持按操作 ID 查询时先查询；若支持符合约定的幂等键，则使用**同一个**操作 ID 和同一请求安全重试；两者都不支持时，可能需要人工对账或补偿。调用方自己记住一个 ID，不能让不支持幂等的下游自动变安全。

## 2. 动手运行

代码使用 Python 3.10+ 的标准库、内存 SQLite 与模拟服务；所有数据都是虚构的。在仓库根目录运行：

```bash
cd examples/agent-ticket-workflow
python3 workflow.py
python3 -m unittest -v
```

预期输出包含“响应丢失”“工单数量：1”，随后 4 条测试通过。这里的服务故意在数据库提交之后抛出 `TimeoutError`，以模拟**写入成功、响应丢失**；第二次用同一个操作 ID 请求，模拟服务返回原操作，而没有新增工单。

[完整可运行代码和测试](https://github.com/xiaoqianbaobao/ai-guide/tree/main/examples/agent-ticket-workflow)中的核心逻辑：

```python
if approval.draft_fingerprint != fingerprint(draft):
    raise PermissionError("draft does not match approval")
return service.create(approval.operation_id, draft)
```

`fingerprint` 对租户、目标和内容的规范化表示计算摘要。测试覆盖目标变化、同一操作 ID 被用于不同内容，以及两个独立操作各创建一张工单。摘要用于检测内容是否变化；它**不会证明审批人身份，也不能替代服务端权限校验**。

## 3. 每个边界为什么重要

### 批准的是一次具体操作

只记录“用户批准过”不够：审查界面至少应展示谁在对哪个目标执行什么内容。审批记录需要绑定可信身份、租户、完整内容或其稳定摘要、操作 ID、有效期和必要的策略版本。目标或内容改变，重新校验并按政策重新审批。

本例用 Python 对象手工构造 `Approval`，任何本地代码都能伪造它。真实系统必须由服务端在完成身份认证和授权后创建并持久保存审批记录；执行器重新校验权限，不信任模型或浏览器传来的“已批准”。

### 操作 ID 是同一意图的稳定标识

在第一次发送前生成随机且不包含个人信息的操作 ID；重试同一次意图使用相同 ID、目标和参数。不同的业务意图即使内容完全相同，也应有不同操作 ID。测试中的 `operation-1` 只是便于阅读的固定示例，不适合作为实际唯一标识生成方案。

模拟服务用数据库唯一键保存结果；若同一 ID 对应不同内容，显式报错。真实供应商的幂等键作用域、保留时长、并发行为与失败处理可能不同，不能假设所有接口都和示例一样。例如 Stripe 的 [API 幂等请求文档](https://docs.stripe.com/api/idempotent_requests)分别说明了 API v1 和 v2 的行为，接入时应按当前版本核对。

### 把未知状态当成未知

真实的服务还需持久记录 `待审批 → 已批准 → 提交中 → 已确认 / 结果未知 / 失败待处理`。结果未知不是“失败”的同义词，也不应直接显示“创建成功”。系统重启后，恢复器根据已持久化的操作 ID 查询或重试，并向用户说明仍在核对。

本例只模拟一次进程内调用，没有持久化审批、状态机、队列、审计、并发冲突处理、恢复器、身份验证或真实 HTTP。`sqlite3` 的事务只约束示例的模拟下游，并不能让跨服务操作自动变成一个原子事务。

## 4. 将练习扩展成验收

1. 修改目标后使用旧批准执行：确认被拒绝且工单数仍为 0。
2. 在“提交前”和“提交后响应前”分别制造故障：比较两种情况下客户端知道什么。
3. 用一个新的操作 ID 重试刚才的未知结果：观察为什么可能创建第二张工单；再讨论如何在客户端持久保存原 ID。
4. 改写模拟服务，让它不支持查询和幂等：设计人工核对步骤，而不是假装能够保证只执行一次。
5. 加入审批人和权限服务之前，先画出信任边界：哪些字段由服务端生成，哪些内容可能受模型或用户控制。

下一步应当把这个教学模拟与[企业级 Agent 实战路线](./enterprise-agent-roadmap)中的身份、审批记录、审计和恢复演练连接起来，逐项替换模拟部件并增加集成测试。
