# 企业知识的权限与撤回：从文档到 Agent 回答

客服问“退款需要核对什么”。Agent 找到一份规则并回答；第二天规则被撤回。此时，原文不再出现在数据库查询里，是否就意味着旧内容不会再被使用？如果另一个租户问到同一主题，系统又如何决定它能看到什么？

本文沿用[企业知识与工单助手](../agent/cases/enterprise-agent-local-lab)的虚构数据，先运行真实的本地教学代码，再分析生产系统还需要补齐的环节。示例使用固定演示身份，没有真实认证、向量索引或生产权限系统。

## 1. 先画数据流，再谈删除

```text
权威文档 → 导入与版本记录 → 索引或缓存 → 授权检索 → 模型上下文 → 回答
     │             │             │             │             │
     └─────────────┴──────撤回 / 权限变更通知与核验───────────┘
                       日志、历史版本和备份另有保留策略
```

不同副本有不同用途：索引用来搜索，缓存加速，历史版本支持审计，回答可能已经展示或发送。撤回源文档不是跨系统的“撤销键”。即使后续查询被阻断，已经交给外部服务或用户看到的数据也需要依据实际合同与系统能力分别处理。

| 层次 | 至少记录或检查 | 一个反例 |
| --- | --- | --- |
| 来源 | 文档 ID、负责人、版本、有效状态、来源及适用范围 | 两份规则同名但来自不同部门 |
| 索引 | 来源版本、租户、访问策略及索引构建状态 | 正文已撤回，旧切片仍可检索 |
| 请求 | 服务端可信身份、当前资源权限、授权决策 | 不能采信模型自行填写的租户 ID |
| 回答 | 引用 ID、版本、生成时点及必要的复核状态 | 引用存在但内容不支持结论 |
| 运维 | 最小必要审计、故障处理、保留与删除责任 | 日志或备份意外保留敏感正文 |

这里的生命周期设计是工程方法，不是适用于所有行业的法定期限；具体保留与删除义务需要按适用规则和合同确认。

## 2. 本地动手：过滤、更新、撤回

在仓库根目录执行。测试会启动本机随机端口的服务并创建临时数据库，不会连接模型或外部业务系统：

```bash
cd examples/enterprise-agent-lab
python3 -m unittest \
  test_server.ApiTests.test_knowledge_is_filtered_by_tenant \
  test_server.ApiTests.test_document_update_withdrawal_and_history \
  test_server.ApiTests.test_concurrent_document_updates_reject_stale_revision -v
```

预期三项通过。第一项检查客服无法得到人事原文；第二项检查只有同租户审核人能修改或撤回规则，更新后旧词不再命中，撤回后新词也不再命中，重启不会让它重新生效；第三项让两次更新基于同一旧版本竞争，结果是一项成功、一项冲突。

核心查询先限定租户和有效状态，再在授权集合内匹配：

```python
rows = db.execute(
    "SELECT id, text, revision FROM documents WHERE tenant = ? AND active = 1",
    (identity.tenant,),
).fetchall()
```

代码取自教学服务的查询路径。它只按租户过滤，并使用原文子串匹配；`identity` 在演示里是固定对象，不证明真实用户身份。要亲自发 HTTP 请求，请跟随[文档更新与撤回演练](../agent/cases/enterprise-agent-local-lab#演练知识更新和撤回)。

## 3. 检索授权和排序为何要一起考虑

假设搜索引擎先在所有租户文档中取最相似的 10 条，再从中删去无权限内容。即使最后没有直接显示其他租户的正文，也可能出现两个问题：授权文档被挤出前 10 条而漏召回；不同的耗时、分数或结果数量可能暴露额外信息。后者是否可利用取决于具体实现与攻击条件，不能仅凭架构图断言发生了泄露。

### 动手：同一排名，不同过滤顺序

下面是预先排好顺序的**虚构数据**，不是向量数据库或性能测试。把代码保存为 `filter_order.py`，用 `python3 filter_order.py` 运行：

```python
# 分数和权限仅用于说明，真实授权应由可信服务端身份决定。
ranked = [
    {"id": "hr-1", "tenant": "hr", "score": 0.99},
    {"id": "hr-2", "tenant": "hr", "score": 0.95},
    {"id": "support-1", "tenant": "support", "score": 0.90},
]
tenant, limit = "support", 2

# 两个方法都不向客服返回人事正文；差异在于候选截断顺序。
post_filter = [d["id"] for d in ranked[:limit] if d["tenant"] == tenant]
pre_filter = [d["id"] for d in ranked if d["tenant"] == tenant][:limit]
print("截断后过滤:", post_filter)
print("授权范围内取前两条:", pre_filter)
assert post_filter == []
assert pre_filter == ["support-1"]
```

这里两条人事记录先占满了候选名额，因此后过滤得到空结果；先限定可见范围再取前两条，则保留客服记录。实验只说明这个排序例子里的召回差异，**不证明某个真实引擎采用哪种算法，也不证明侧信道泄露存在**。生产实现还需确认过滤在引擎内部如何执行、候选池如何选择，并在权限变更后重新验证缓存。

设计时应检查搜索服务的过滤位置、向量索引隔离、结果及错误返回、权限更新延迟，以及缓存键是否绑定用户或授权范围。[Microsoft 的 RAG 文档](https://learn.microsoft.com/en-us/azure/foundry/concepts/retrieval-augmented-generation)建议在检索阶段实施访问控制；[OWASP 对向量与嵌入风险的讨论](https://genai.owasp.org/llm2026/llm092026-vector-and-embedding-weaknesses/)也提醒评估检索链路中的访问边界。不同搜索产品的过滤语义不同，必须查对应版本文档并用真实配置验证。

## 4. 撤回后如何验收

以撤回 `refund-v1` 为例，先明确每一层的负责人和目标时限，再逐项留下测试证据：

1. **源与授权**：撤回操作需要有权人员；并发版本冲突不能悄悄覆盖。撤回后当前查询不返回该版本。
2. **索引与缓存**：构造过期副本，验证更新事件丢失、延迟与重放时的处理；不要只测试理想的即时同步。
3. **在途任务**：在生成期间撤回文档，检查回答展示前是否重新核验。现有[模型工具循环](../agent/cases/enterprise-agent-model-tool-loop#资料在生成答案期间变了怎么办)有离线模拟，但检查之后仍存在时间窗口。
4. **历史、日志与备份**：确认谁能访问旧版本、保留多久、如何删除或恢复；日志不要默认写入文档正文。
5. **已发出内容**：记录是否已发送给用户或外部服务，明确通知、更正或其他业务处理方式；后续撤回无法自动收回已发送数据。

示例的历史表保留旧文本，目的是教学观察，**不等于推荐无限保留**；演示也没有实现向量索引、缓存失效或真实删除证明。

## 5. 失败演练与练习

为一个虚构租户设计测试：A 用户能看文档、B 用户不能看；缓存预热后撤销 A 的权限，再分别用两人请求。列出正常回答、拒答、引用、日志和缓存的预期；接着模拟撤回事件未到达索引，写出系统应阻断、告警还是人工处理，以及每种选择对可用性的影响。

如果系统让模型调用外部工具，还要检查数据是否可能从工具参数或模型输出流出；检索授权不能取代[工具调用的服务端鉴权](../02-agent-core/agent-security-boundaries)。
