# 你正在经历的，是软件开发的第三次范式转移

## 你是否想过这个问题

为什么很多开发者已经在用 AI 写代码，但工作方式仍然没有质变？

答案通常不在模型能力，而在心智模型。

很多人只是把 AI 当作更快的补全工具，却没有意识到它正在改写任务拆解、上下文组织和验证流程。

如果你还沿用旧范式去驱动新工具，AI 的价值就会被压缩成“帮你少打几行字”。

## 三次范式的变化

### 第一次：人适应机器

早期编程强调精确、低层、机械。

开发者必须完全遵守机器的表达方式，关心寄存器、指令和执行顺序。那时最核心的能力，是把人的意图尽可能压缩成机器能够理解的严格格式。

### 第二次：人描述结构

高级语言、声明式框架、SQL、容器编排逐步出现。

开发者开始更多描述目标结构，而不是穷举所有底层步骤。你不再需要亲自管理每一个细枝末节，而是通过更高层的抽象组织系统。

### 第三次：人描述意图

在 AI 原生系统里，开发者不只是写逻辑，还要：

- 描述目标
- 提供背景
- 组织上下文
- 约束行为
- 设计验证闭环

这意味着开发者的价值并没有下降，只是正在转移。

过去你主要负责把每一步写清楚，现在你还要负责让系统知道“为什么做、看到什么、做到什么程度算完成”。

## 为什么这次变化本质不同

过去的软件系统大多是确定性的。

给定输入、逻辑和环境，输出基本稳定。即使系统复杂，它依然遵守清晰的因果链。

但大模型引入了一个概率性的推理单元。它能力很强，却不保证每次都按同样路径工作。

这不是简单的“结果有点波动”，而是整个工程关注点发生了变化。

这意味着工程重点开始转移：

- 从把每一步写死转向给出足够好的约束
- 从只测试结果转向同时评估轨迹和结果
- 从单段代码优化转向整体上下文策略设计

## 旧范式是怎样限制你的

如果你还用传统的方式驱动 AI，常见表现通常是：

- 任务描述只给一句话，没有目标边界
- 把复杂任务当成一次性问答
- 得到结果后完全手工检查
- 每次失败都重新来过，没有积累和反馈

这种方式当然能工作，但它无法稳定扩展。

一旦任务变复杂，你就会遇到熟悉的问题：

- 输出看似正确，但方向跑偏
- 任务中途忘记原始目标
- 遇到错误时不会恢复
- 每一轮都像重新开始

## 新范式要求你做什么

AI 原生开发要求你从“写确定步骤的人”变成“设计协作系统的人”。

你开始要关心的，不只是代码本身，还有：

- 任务是否可拆解
- 上下文是否完整
- 工具是否清晰可调用
- 状态是否能被保留
- 结果是否有验证机制

这也是为什么 AI Agent 开发最终会自然延伸到 Tool Use、Memory、RAG、多 Agent 和 Eval。

## 一个直观对比

下面是同一个任务，在两种范式下的描述差异。

```text
旧范式：
请帮我做一个文章总结。

新范式：
请阅读下面的文章内容，提取 3 个核心观点。
输出格式必须是 JSON，字段为 title、points、risks。
如果原文信息不足，请明确标记 unknown，不要补充猜测。
```

两者的差别不在礼貌程度，而在系统约束质量。

第二种描述其实已经隐含了新范式的几个核心动作：

- 明确目标
- 约束输出
- 控制幻觉
- 让结果更易验证

## 最小实验：感受范式差异

下面这个示例不是为了真正调用模型，而是为了对比“描述步骤”和“描述意图”两种任务设计方式。

```python
task_old = "帮我整理一个 Python 学习计划"

task_new = """
请为有基础编程经验、准备进入 AI Agent 开发的读者，
设计一个 4 周 Python 学习计划。

要求：
1. 每周给出目标、练习内容和产出物
2. 内容要覆盖脚本、文件、JSON、异常处理
3. 输出使用 Markdown 二级标题组织
4. 如果某一周依赖前置知识，请明确写出
"""

print("旧范式任务：")
print(task_old)
print()
print("新范式任务：")
print(task_new)
```

这段代码本身很简单，但它揭示了一个事实：

同样是“提需求”，AI 原生任务设计已经更接近系统设计，而不是一句口头要求。

## 这对工程师意味着什么

从长期看，AI 并不是在削弱工程能力，而是在提高工程能力的抽象层级。

真正有竞争力的开发者，会越来越擅长下面这些事：

- 把模糊目标变成清晰任务
- 把复杂任务拆成可验证步骤
- 为模型设计稳定上下文
- 用工具和测试把不确定性关进笼子里

所以，AI 原生开发不是少写代码，而是要在“代码之外”做更多关键设计。
