## 为什么你需要一条学习路径

AI Agent 相关内容有一个很明显的问题：概念多、术语杂、热点快，而且很多文章只讲局部。

如果没有路径感，你很容易陷入下面几种状态：

- 今天看 Prompt，明天看 Agent，后天看 RAG，但一直串不起来
- 学了很多名词，却不知道它们在系统里分别解决什么问题
- 一上来就追框架和 Demo，结果越学越碎
- 看似学了很多，真正动手时还是不知道先做什么

这套站点的目标，不是把所有热点都堆进来，而是提供一条尽可能稳定的认知主线：

1. 先理解范式为什么变化
2. 再理解模型是什么、擅长什么、不擅长什么
3. 再进入 Agent、Memory、Multi-Agent 等机制层
4. 最后回到工具、评估和工程闭环

所以，最重要的不是“把所有文章都看完”，而是“按适合自己的顺序建立心智模型”。

## 先记住这条主线

如果你只想先记住一件事，可以记这条最核心的学习顺序：

```text
序章 -> 语言模型基础 -> Agent 核心机制 -> Memory -> 多 Agent -> 工具与框架 -> 评估与进化
```

这条顺序背后的逻辑是：

- `序章` 解决视角问题
- `语言模型基础` 解决对象认知问题
- `Agent 核心机制` 解决行动闭环问题
- `Memory` 解决任务连续性问题
- `多 Agent` 解决复杂协作问题
- `工具与框架` 解决实现和选型问题
- `评估与进化` 解决系统优化问题

如果你总觉得“每个概念都懂一点，但为什么连不起来”，通常就是因为缺少这条主线。

## 三条推荐路径

不同读者的起点不一样，所以最合理的读法也不完全一样。

### 路径 A：已经在用 AI 工具，但缺少底层理解

适合这类读者：

- 已经在用 Cursor、Claude Code、Trae 或其他 AI 工具
- 能明显感受到效率变化，但不稳定
- 遇到复杂任务时，不知道为什么 AI 有时好用、有时失灵

建议顺序：

1. 先读 `序章`
2. 再读 `语言模型基础`
3. 然后进入 `Agent 核心机制`
4. 最后按兴趣补 `Memory` 和 `评估与进化`

这条路径的目标不是先学“怎么搭系统”，而是先搞清楚：

- 你到底在和什么系统协作
- 为什么上下文和任务定义这么重要
- 为什么模型一进入多步任务就容易暴露问题

### 路径 B：希望系统学习 AI Agent 工程

适合这类读者：

- 希望从概念走到完整工程理解
- 想自己设计、搭建或改造 AI Agent 系统
- 不满足于只会用单个工具

建议顺序：

按 `序章 -> 语言模型基础 -> Agent 核心机制 -> Memory -> 多 Agent -> 工具与框架 -> 评估与进化` 的顺序完整推进。

原因很简单：

- 前三部分构成系统基础
- `Memory` 和 `多 Agent` 是能力扩展
- `工具与框架` 是实现层视角
- `评估与进化` 决定系统能不能长期变好

如果你跳过前面直接看后面，容易学成“术语认识很多，但系统结构不清楚”。

### 路径 C：编程基础还不稳

适合这类读者：

- 能看懂一些代码，但工程经验不强
- 看到工具调用、文件读写、脚本处理就有点吃力
- 想学 Agent，但担心自己基础不够

建议顺序：

1. 先补齐基础编程、文件处理和脚本能力
2. 阅读 `序章` 建立整体认知
3. 进入 `语言模型基础` 和 `Agent 核心机制`
4. 先不急着追多 Agent 和复杂框架

你不需要等“什么都会了”再来学 Agent，但需要知道一个事实：

Agent 工程本质上会大量碰到这些能力：

- 读写文件
- 组织 JSON / YAML
- 调接口
- 处理异常
- 跑脚本和看日志

基础越稳，后面的理解会越轻松。

## 常见误区

### 误区一：先追最火的框架

很多人一开始就去看一堆框架名词，结果很快迷失。

这是因为框架解决的是“如何更快实现”，而不是“为什么系统要这样设计”。  
如果底层心智模型没建立，框架学得越多，越容易混乱。

### 误区二：只看概念，不做映射

如果你读完一篇文章后，不能回答下面三个问题，那通常说明还没有真正吸收：

- 这个概念解决什么问题
- 它和前后模块是什么关系
- 它在实际系统里表现为哪类组件或行为

所以学习时要不断做“概念 -> 系统角色 -> 工程位置”的映射。

### 误区三：试图一次看完全部内容

这类站点更适合“主线推进 + 局部回看”，而不是从头到尾机械刷完。

很多文章第一次阅读时只需要抓住主结论，等真正做项目时再回来细读工程细节，效果反而更好。

## 每篇文章应该怎么读

一篇文章并不是只要把正文扫过去就够了。更高效的读法通常是下面这个顺序。

### 第一步：先看你在知识体系里的位置

每篇文章顶部都有 `KnowledgeMap`。  
它的作用不是装饰，而是帮助你理解：

- 你现在属于哪个模块
- 这篇文章在整体知识链路里处于什么位置
- 读完后应该往哪里走

当你总觉得内容零散时，先看位置，能帮你恢复主线感。

### 第二步：看文章头部信息

`ArticleHeader` 会告诉你：

- 所属模块
- 标签类型
- 阅读时间
- 先修要求
- 文章摘要

这能帮助你快速判断：

- 现在适不适合读这篇
- 该用“扫一遍”的方式，还是“做笔记”的方式

### 第三步：抓住核心问题

大多数文章都会先回答一个关键问题，例如：

- 为什么需要这个概念
- 它常被误解成什么
- 它和相邻概念有什么边界

先抓住这个问题，再进入细节，阅读效率会高很多。

### 第四步：把文章内容映射到系统结构里

阅读时建议你主动做这样的转换：

- LLM 是什么能力边界
- Agent 解决什么执行问题
- Memory 解决什么连续性问题
- Eval 解决什么优化问题

一旦你能把文章内容映射成系统角色，知识就不会只停留在名词层。

### 第五步：读完立刻决定下一步

不要把阅读停在“懂了”。  
每读完一篇，最好立刻做一个决定：

- 继续顺着主线往下
- 回到模块首页补上下文
- 去相邻文章做概念对照
- 把当前文章对应到自己正在做的项目上

这样知识才会真正连起来。

## 如果你是按项目来学

有些读者不是来系统读书的，而是手上已经有一个项目。  
这时更适合按问题倒推路径。

你可以这样选：

- 如果你搞不清模型为什么经常答偏，先读 `语言模型基础`
- 如果你想让系统自己调用工具做事，先读 `Agent 核心机制`
- 如果你发现系统老忘上下文或依赖外部资料，先读 `Memory`
- 如果你已经有系统，但效果不稳定，先读 `评估与进化`
- 如果你在多个工具、框架和产品之间犹豫，先读 `工具与框架`

也就是说，主线顺序适合建立体系，问题驱动顺序适合带着项目回查。

## 一套简单的学习节奏

如果你想更稳一点，可以采用一个很实用的节奏：

1. 每次先读一个模块首页
2. 再挑 1 到 2 篇关键文章精读
3. 读完后写一句“这个模块主要解决什么问题”
4. 遇到项目卡点时回站内查相应模块

这个节奏的好处是，你不会把阅读和实践割裂开。
