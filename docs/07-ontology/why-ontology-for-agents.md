# 为什么 Agent 系统需要明确业务语义

<ArticleHeader module="本体论与知识表示" :tags="['进阶', '建模']" reading-time="12 分钟" prerequisite="了解 Agent、工具调用和基础数据建模" summary="用供应商身份混淆案例理解概念定义、实体映射与业务治理，区分语义模型和实际执行权限的系统。" />

两个 Agent 都在处理“供应商 42”。采购系统中的 42 代表采购组织，合同系统中的 42 代表签约法人。它们名字相同，并不代表是同一个实体。如果系统仅凭名称或数字 ID 合并记录，后续风险判断和审批可能落到错误对象上。

这个问题不是加一个更长的提示词就一定能解决。团队需要先约定对象、身份、关系与来源的含义，再让数据处理和业务服务按约定检查。本文用虚构案例解释这一过程；它不要求所有项目采用特定本体平台。

## 1. 同一个词，可能指不同对象

假设一次风险事件涉及采购方和签约法人：

| 来源 | 原字段 | 实际含义 | 错误合并后的后果 |
| --- | --- | --- | --- |
| 合同系统 | `supplier_id=42` | 签约法人 | 把法人的合同责任错归给采购组织 |
| 采购系统 | `supplier_id=42` | 采购组织 | 把采购组织的工作流写到法人记录 |
| Agent 的文字总结 | “供应商 42” | 含义不明 | 下游无法判断要更新哪一个对象 |

先询问业务负责人：这些对象能否一对一映射？是否存在一个法人对应多个采购组织？各系统 ID 如何命名与维护？把答案记录下来，再决定数据结构和映射规则。如果无法确定，就保留歧义并交由人确认，不要让模型自行猜测。

## 2. 动手：让身份包含类型与来源

以下 Python 例子使用**虚构映射**。它说明为什么不能只用裸数字做跨系统身份；真实系统还需要处理租户、映射更新、合并拆分和访问权限。

```python
# 键包含对象类型、来源系统和来源 ID；值是内部规范 ID。
identities = {
    ("legal_entity", "contracts", "42"): "legal:acme-cn",
    ("purchasing_org", "procurement", "42"): "org:east",
}


def resolve(kind, source, external_id):
    key = (kind, source, external_id)
    if key not in identities:
        raise LookupError("身份未确认，不能自动合并")
    return identities[key]


legal = resolve("legal_entity", "contracts", "42")
organization = resolve("purchasing_org", "procurement", "42")
print("签约法人:", legal)
print("采购组织:", organization)
assert legal != organization
```

预期输出两个不同 ID。例子只是查一张硬编码表，不代表已经实现实体消歧、数据库一致性或生产权限；映射本身可能出错，也应保留来源、责任人和变更记录。

## 3. 本体、数据模式和运行时各管什么

在知识表示中，本体用于定义领域中的概念、关系及其语义；具体能表达哪些约束取决于使用的语言和系统。[W3C 的 OWL 2 入门文档](https://www.w3.org/TR/owl-primer/)用类、属性与公理解释了一种形式化方式。概念定义有助于团队沟通和数据集成，但定义不会自动变成可靠的执行权限。

| 层面 | 本例需要回答的问题 | 可能的实现 |
| --- | --- | --- |
| 业务语义 | “供应商”“签约法人”“采购组织”分别指什么？ | 术语表、领域模型或形式化本体 |
| 数据结构 | 对象、关系、来源 ID 如何存储和关联？ | 数据库表与约束、图模式或其他数据结构 |
| 写入治理 | 谁可修改映射？哪些变化需要审核？ | 身份系统、服务端授权、审批记录和事务 |
| 评估与维护 | 映射何时过期？错误如何发现和修复？ | 样本集、版本、审计和人工复核流程 |

这些层面可以使用同一平台，也可以由多个系统协作；没有一种存储或建模名称能替代真实的身份检查、测试和运维。更多概念区分见[分类、本体、知识图谱与 RAG](./ontology-vs-taxonomy-kg)。

## 4. 两种产品如何组合这些能力

[Palantir 的 Ontology 权限文档](https://www.palantir.com/docs/foundry/object-permissioning/ontology-permissions)区分本体资源、实际对象数据以及动作相关的权限。它展示的是**特定平台**如何把语义资源与权限机制结合；产品配置和版本会影响实际行为，不能推断所有本体都自带相同能力。

[Cruxible 项目](https://github.com/cruxible-ai/cruxible)将其描述为面向 Agent 的受治理状态引擎，提供领域模型、写入与审查等机制。本站[Cruxible 建模文章](./cruxible-yaml-ontology)使用历史版本讲解；尝试运行时应核对当前版本文档与配置。两者可以作为设计参考，是否适合你的组织还要依据部署、权限、费用、维护与实际验证结果判断。

## 5. 什么时候值得投入更多建模

- **先从轻量约定开始：** 单团队、低风险的知识问答可以先统一术语、来源 ID 和更新责任人，再观察是否确实需要更形式化的表示。
- **优先加强语义与治理：** 跨系统共享对象、多个团队使用相同事实，或 Agent 会提出涉及审批和外部写入的操作时，身份映射、版本、责任和授权错误的代价通常更高。
- **不设机械门槛：** 不存在“两个 Agent 就必须上某个平台”这样的通用规则。先盘点失败后果和查询需求，再比较简单表结构、领域模型与更形式化方案的成本。

即便只是问答，敏感资料的读取仍需要权限控制；即便已经有成熟本体，写入业务系统也仍需独立授权与安全测试。

<span id="_5-最低成本起步-不做-大全-就做四层最小可行本体论-minimum"></span>

## 6. 一个可以交给团队讨论的最小方案

1. 选一个具体流程，例如供应商风险判断；记录一次真实工作里涉及的对象与角色。
2. 为每种对象写定义、来源系统、标识规则和一个反例；向业务负责人确认。
3. 选两条必要关系，写清方向、来源和更新时间；为未知或冲突状态保留处理方式。
4. 对可能改变业务状态的操作，写下服务端身份、审批、事务与失败恢复要求。
5. 准备正常、身份歧义、无权限和来源过期的测试，用结果推动下一次修订。

先用可维护的术语表、表结构和测试也可以；当需要跨系统复用与形式化推理时，再评估更严格的建模方法。关键是**定义、实现和验证能互相对照**。
