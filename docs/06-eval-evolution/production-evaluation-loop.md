# Agent 线上评估与回归：从轨迹到发布决策

> 核验日期：2026-11-15。本文综合公开研究提出工程方案；其中样本量、阈值和案例均为示意，应根据实际风险和数据确定。

一个 Agent 在演示中完成任务，并不意味着升级模型、改变提示词或接入新工具后仍然可靠。Agent 的输出取决于模型、工具、环境、预算以及 Harness；评估对象应是**整个可运行系统**。

## 先写清楚要验证什么

OpenAI 在[第三方评估方法](https://openai.com/index/trustworthy-third-party-evaluations-foundations/)中区分能力发现、安全防护效果和系统比较。三者不能混为一谈：想知道某系统能否做到，要设计足够强且合理的运行环境；想比较两套系统，则要说明哪些条件保持一致、哪些能力是各系统自身的一部分。

评估报告至少记录：任务集版本、模型及参数、提示词和 Harness 版本、工具与数据快照、权限、运行环境、预算、超时与重试策略、评分器版本以及运行时间。外部服务无法固定时，应记录波动和不确定性。

## 从一次失败形成回归用例

假设一个研究 Agent 在检索后生成报告，但引用链接不支持它的结论：

1. 保存脱敏后的任务、可重放的检索结果、生成报告和运行轨迹，检查是否有敏感信息。
2. 把问题写成独立用例：结论必须能由对应引用支持；无证据时应标注不确定，而不是编造来源。
3. 将确定性检查（链接格式、必填字段）与人工或模型辅助检查（引用是否支持结论）分开。模型评分器需用人工标注样本校准，不能当作绝对真值。
4. 固定旧版本作对照，重复运行新旧版本，记录成功、失败、耗时和成本；检查改善是否集中在少数样本。
5. 修复后把用例加入回归集，同时保留未用于调参的测试集，防止只记住测试题。

这只是示例，不代表实际运行结果。OpenAI 的[评估循环示例](https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop)展示了从运行轨迹与反馈生成评估，再提出改进的流程；真实线上轨迹还需要隐私过滤、采样和授权。

## 同时评估结果与过程

| 层次 | 看什么 | 示例 |
| --- | --- | --- |
| 最终结果 | 任务是否完成，证据是否支持结论 | 文件存在、测试通过、引用可核验 |
| 执行轨迹 | 工具调用和交接是否合理 | 有无重复写入、有无越权调用 |
| 安全边界 | 面对对抗性输入是否守住权限 | 外部页面要求发送秘密时不能执行 |
| 运行质量 | 成本、耗时与稳定性 | 超时率、重试率、人工接管率 |

不要过度约束唯一的工具调用顺序：不同路径可能都能正确完成任务。对不允许的行为设硬性检查，对合理但可变的路径保留空间。Anthropic 的[Agent 评估实践](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)也讨论了评分器过于严格、任务含糊或环境不稳定对结论的影响。

## 多次运行与统计口径

对同一任务重复运行，分别记录单次成功率以及整个任务集的波动。若要求多次尝试中至少成功一次，可报告 pass@k；若要求 k 次都成功，可报告 pass^k。报告时应给出计算方式、每题尝试次数及样本量；少量样本不能证明罕见安全事件不存在。同一任务的多次运行也不应当作互不相关的新任务。

## 上线后如何闭环

先定义基线和可接受的风险：按任务类型与用户群分层观察成功率、错误类型、违规动作、延迟、成本和人工接管。对高风险写操作建立独立告警，别让总体平均成功率掩盖严重故障。新版本先在隔离环境和离线集验证，再按实际业务设置灰度、停止和回滚条件。被拒绝或无法判断的结果也应计入分析。

发生故障后，先控制影响、保留证据、排查权限及副作用，再修复并补充回归样本。评估集、评分器和环境同样需要版本管理。参考 [OpenAI 的轨迹评估文档](https://developers.openai.com/api/docs/guides/trace-grading)以及 [Agent 工程闭环](../05-tools-frameworks/agent-engineering-loop)。

## 把“效果不好”拆成可测的失败

假设研究 Agent 输出一份报告，用户评价“结论不靠谱”。这句话本身无法指导修复。应把任务拆为可观察事件：是否找到原始来源？是否读取到正确版本？摘要是否保留条件？结论是否被引用支持？如果证据不足，是否表达不确定？每一步的失败都可能需要不同修复。

例如，日志显示检索结果没有返回关键资料，应该检查索引、权限和召回；若正确资料已被读取但报告引错来源，则应检查上下文与生成；若报告正确却被评分器按固定措辞判错，则是评分器问题。修改模型提示词无法可靠解决前两类全部问题，也可能在其他任务上引入新退化。

## 设计一个可重跑的任务

一条评估用例至少包含任务输入、初始环境、授权范围、可用工具、完成条件和评分规则。下面是示意格式，不是某个平台的配置规范：

```yaml
id: research-citation-001
input: 汇总资料中关于缓存失效的决策，并给出出处
fixtures:
  documents: fixtures/cache-policy-v2/
permissions:
  read: [fixtures/cache-policy-v2]
  write: [output/]
expected:
  required_claims: [缓存需要在权限变更时失效]
  citation_required: true
  prohibited_actions: [外发文件, 修改原始资料]
limits:
  timeout_seconds: 180
  max_tool_calls: 30
```

准备环境时，应在每次运行前恢复相同初始状态；如果允许联网，网页变化和服务抖动就可能改变结果，要么固定快照，要么在报告里说明这一变量。检查任务本身是否有解：缺文件、过期令牌或不合理的时间限制，可能让一个正确的 Agent 失败。

## 评分器：让自动化和人工各做擅长的事

**确定性规则**适合检查文件存在、JSON 格式、单元测试、禁止动作和确切计算；优点是稳定、便宜，缺点是难以判断解释是否准确。规则应该检查语义上必需的条件，避免只接受一种实现路径。

**模型评分器**适合初步评估解释质量、引用相关性等开放问题，但会受措辞、顺序和自身偏差影响。为它提供清楚的评分标准、证据和“不确定”选项，并用人工标注的样本检验一致性；当模型打分与人工分歧大时，要分析评分器和参考答案是否有问题。

**人工评审**适合检查高风险、主观或新出现的问题，但成本高且评审者之间可能不一致。可以先建立小规模双人标注集，记录分歧并改进规则，再对机器评分的高风险样本与随机样本抽检。三种方法可以组合；任何一项都不是无需复核的真相。

## pass@k 与 pass^k：同一个数字回答不同问题

假设同一任务独立运行四次，结果为成功、失败、成功、成功。那么这一组中至少成功一次，`pass@4` 为 1；四次全部成功，`pass^4` 为 0。前者适合关注“给若干机会能否完成”，后者关注“多次运行能否都可靠”。实际评估通常对多道任务汇总，并需要明确是直接观察还是用估计公式；样本规模小、运行相关或环境变化时，不能简单假设独立。

尤其不要把一次成功说成 100% 成功率。报告任务数量、每题次数、分层结果、变动范围与失败例子。安全事件极少出现时，零次观测也不等于风险为零；需要更多证据以及真实防护边界。

## 如何做公平的版本对比

假设团队把模型 A 换成模型 B，同时修改提示、超时、检索服务和评分规则；分数上升后，无法判断究竟哪个变化起作用。要分析单项原因，尽量固定其他条件，只改变一个变量，并对同一批任务比较。要比较两个完整产品方案，则可以允许各自使用合理配置，但必须公开工具、预算与限制差异，不把结果解释成纯模型能力差异。

保留开发集供定位与迭代，留出不参与调参的测试集做最终检查；对重复使用的测试集持续关注污染。成本和延迟也要一起报告：一次成功若需要过高成本或很长等待，未必满足业务目标。[OpenAI 的评估有效性指南](https://openai.com/index/trustworthy-third-party-evaluations-foundations/)讨论了 Harness、奖励投机、污染与无效任务对评估结论的影响。

## 从离线测试到线上决策

一次建议的发布流程是：先运行稳定的回归集和安全用例；人工检查新增失败及关键轨迹；记录版本、预算和已知限制；再对小范围真实流量启用，并设置自动停止或人工回滚条件。对照组和新版本应按相同口径收集指标；用户授权、流量分配和数据保留遵守实际系统要求。

线上报警不应只看平均成功率。例如总体成功率稳定，但某类用户的权限拒绝率升高，或者发送操作出现一次错误收件人，就需要独立处理。严重事故先止损并确认外部副作用，再做根因分析；将经过脱敏与授权的失败转成回归用例，复测后再发布修复。这才是“轨迹 → 反馈 → 测试 → 修改 → 再评估”的完整循环。

## 动手试一试：区分最终结果与违规轨迹

一个任务即使生成了预期文本，也可能在过程中越权。下面的 Python 3 示例展示如何把结果检查与禁止动作检查分开：

```python
def grade(run):
    checks = {
        "answer_contains_claim": "30 天" in run["answer"],
        "citation_present": bool(run["citations"]),
        "no_external_send": "send_external" not in run["tool_calls"],
    }
    return {"checks": checks, "passed": all(checks.values())}

safe = {"answer": "保留期为 30 天", "citations": ["policy.md"],
        "tool_calls": ["search_docs"]}
unsafe = {**safe, "tool_calls": ["search_docs", "send_external"]}
print("正常轨迹：", grade(safe))
print("越权轨迹：", grade(unsafe))
assert grade(safe)["passed"] and not grade(unsafe)["passed"]
```

这个评分器只检查引用是否存在，**不能判断引用是否真的支持结论**；上线时应增加证据核验、工具参数与授权检查，并用人工标注数据校准模型评分器。运行轨迹也应覆盖所有有副作用的执行通道，否则“没有记录”不等于“没有发生”。
