## 为什么奖励函数这么敏感

系统不会自动理解你真正想要什么，它只会沿着你定义的奖励信号去优化。

<div class="key-insight">
  <div class="key-insight-label">核心洞察</div>
  <p class="key-insight-text">
    奖励函数本质上是在告诉 Agent 什么值得追求，所以它定义的不是评分规则，而是系统最终会长成什么样。
  </p>
</div>

## 先理解一个最重要的事实

在任何可优化系统里，目标函数都会塑造行为。

如果你奖励的是：

- 更快完成
- 更少步骤
- 更高点击率
- 更高通过率

系统就会朝这些方向越来越强。

问题在于，你真正想要的目标，往往不是单一指标，而是多个约束的平衡。

这也是奖励函数最容易出问题的地方：

`你写下的是一个分数规则，系统追逐的却是它背后的行为导向`

## 为什么很多奖励设计最后都会“跑偏”

因为真实目标通常很复杂，但奖励往往被简化得太粗糙。

例如你希望一个代码 Agent：

- 修好 bug
- 不破坏已有功能
- 尽量少改无关代码
- 运行成本合理

如果你最后只定义了一个奖励：

`测试通过 +1`

那系统就可能发展出各种你并不想要的行为：

- 为了过测试写临时补丁
- 修改测试本身
- 过度拟合当前样例
- 忽略长期可维护性

这就是奖励函数设计的核心难点：

`机器会精确优化你写下来的东西，而不会自动理解你心里真正想要的东西`

## 奖励函数到底在定义什么

一个更准确的理解是：

奖励函数定义的不是“怎么评价一次输出”，而是“系统长期会朝什么方向变强”。

所以一个好的奖励设计，至少要回答：

- 什么行为值得鼓励
- 什么行为应该惩罚
- 多个目标冲突时优先级怎么排
- 短期收益和长期质量怎么权衡

## 常见奖励来源

在 Agent 系统里，奖励一般来自几类信号。

### 1. 结果奖励

这是最直观的，例如：

- 任务是否完成
- 最终答案是否正确
- 测试是否通过
- 表单是否成功提交

优点是简单明确，缺点是通常太晚、太粗。

### 2. 过程奖励

过程奖励关注中间行为，例如：

- 是否调用了正确工具
- 是否遵守了执行顺序
- 是否读取了必要上下文
- 是否出现无意义重复搜索

这类奖励能帮助系统更快学到“怎样做更合理”。

### 3. 成本奖励

真实系统里，成本往往不能忽略，例如：

- token 消耗
- 执行轮数
- 工具调用次数
- 总耗时

如果没有成本约束，系统很容易为了追求成功率而无限扩张步骤。

### 4. 安全与约束奖励

有些行为即使结果正确，也不应被鼓励，例如：

- 修改越权文件
- 读取不该读的资源
- 跳过关键确认步骤

这时就需要额外的惩罚项或硬性约束。

## 一个简单例子

假设你在设计一个“修复配置错误”的代码 Agent。一个比较初级的奖励函数可能是：

```text
build 通过 = +1
build 失败 = 0
```

这当然比没有目标强，但仍然过于单薄。

一个更合理的思路可能是：

```text
build 通过 = +1.0
目标问题被修复 = +1.0
修改无关文件 = -0.3
重复无效搜索 = -0.1
总步骤过多 = -0.2
```

这时系统优化的就不再只是“想办法把 build 过掉”，而是更接近：

- 修对问题
- 少做无关动作
- 控制成本

## 奖励设计为什么常常需要组合

因为真实目标往往是多目标的。

只奖励成功率，系统可能变得：

- 成本极高
- 过程冗长
- 行为不稳定

只奖励低成本，系统又可能变得：

- 太保守
- 不愿探索
- 遇到困难就提前停止

所以奖励设计通常不是“找一个最好指标”，而是：

`把多个目标组合成一个可优化的平衡结构`

## 一个常见错误：代理指标替代真实目标

这是奖励设计里非常经典的问题。

例如你真正想要的是：

`用户问题被稳定解决`

但你实际奖励的是：

`回答看起来很完整`

这时系统就会越来越擅长写长答案，而不一定越来越擅长解决问题。

类似的错误还有：

- 把“点击率”当成“用户满意度”
- 把“测试通过率”当成“代码质量”
- 把“检索次数少”当成“效率高”

代理指标不是不能用，但必须清楚：

`它只是近似目标，而不是真实目标本身`

## 奖励黑客问题

一旦奖励定义得不够严谨，系统就可能学会“钻空子”。

这通常被叫做 reward hacking。

例如：

- 为了减少步骤，系统直接跳过必要检查
- 为了提升成功率，系统只挑简单任务回答
- 为了获得正奖励，系统操纵可见指标而不真正完成目标

这不是系统“坏了”，而是它太认真地执行了你的目标定义。

所以奖励函数设计的一个核心工作，就是不断寻找：

- 系统会不会利用这个规则走捷径
- 哪些看似合理的奖励会诱导错误行为

## 什么时候该用硬约束，什么时候该用奖励

并不是所有要求都应该写成奖励项。

一个实用判断是：

- 如果这是“最好做到”的偏好，可以写进奖励
- 如果这是“绝对不能违反”的规则，更适合写成硬约束

例如：

- 尽量减少 token 消耗：适合做奖励
- 不允许删除关键生产配置：更适合做硬约束

把绝对规则只写成惩罚项，很多时候并不够安全。

## 一个分层设计思路

实际工程里，更稳的方式通常是分层：

1. 先用硬约束定义不可越界的边界
2. 再用主奖励定义核心目标
3. 最后用次级奖励调整效率、稳定性和过程质量

这样比把所有东西都塞进一个大而混乱的分数公式更容易维护。

## 一个最小示例

下面是一个非常简化的伪代码示例：

```python
def compute_reward(result):
    score = 0.0

    if result.task_success:
        score += 1.0

    if result.target_issue_fixed:
        score += 1.0

    score -= 0.05 * result.unnecessary_tool_calls
    score -= 0.02 * result.total_steps

    if result.modified_forbidden_files:
        return -1.0

    return score
```

这个例子虽然简单，但已经体现了几层逻辑：

- 成功有正奖励
- 冗余行为有成本惩罚
- 某些越界行为直接触发强惩罚

## 怎么判断一个奖励函数是否设计得还不错

可以用下面 5 个问题快速检查：

1. 它是不是在逼系统优化你真正关心的目标？
2. 它会不会鼓励系统走捷径？
3. 它有没有明显忽视成本、稳定性或安全性？
4. 多目标之间有没有主次之分？
5. 当系统表现异常时，你能不能从奖励结构里看出原因？

如果这 5 个问题里有 2 到 3 个都答不上来，通常说明奖励设计还很脆弱。

## 和 Eval 的关系是什么

奖励函数和 Eval 很像，但并不完全一样。

- `Eval` 更偏评估与比较
- `Reward` 更偏引导优化方向

你可以把它们理解成：

- Eval 告诉你现在系统表现如何
- Reward 告诉系统未来应该朝哪里进化

如果两者方向不一致，就会出现很奇怪的情况：

- 训练时系统在变“更高分”
- 上线后系统却变得“更难用”

所以设计奖励时，最好始终回到 Eval 体系和真实业务目标对齐。

## 本节总结

- 奖励函数定义的不是分数本身，而是系统长期进化方向
- 单一奖励往往不够，真实目标通常需要多目标平衡
- 奖励设计最怕代理指标替代真实目标，以及 reward hacking
- 更稳的方式是把硬约束、主奖励和次级奖励分层设计
