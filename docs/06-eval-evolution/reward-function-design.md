## 一个来自清结算系统的对照

上一篇讲到过一个对账异常处理 Agent：给它一笔金额不平的交易，让它查流水、判断异常类型、决定是否需要人工复核。Eval 告诉你这个 Agent 现在做得好不好，而奖励函数决定的是另一件事——如果你要用强化学习或者迭代打磨这个 Agent，它接下来会朝哪个方向变得更"聪明"。

这两者的区别很关键。假设你把奖励定义成"分类结果正确 +1"，系统会精确地朝这一个目标优化，而不会自动理解你心里还有一堆没写进去的隐含要求：不能查询超出权限的字段、不能跳过关键核对步骤、不能为了效率牺牲可追溯性。机器只会优化你写下来的东西，不会优化你心里想的东西——这是奖励函数设计里最容易被忽视,也最容易出事故的一点。

## 常见奖励来源

在 Agent 系统里，奖励一般来自四类信号。

**结果奖励**：任务是否完成、最终判断是否正确、流程是否走完。优点是简单明确，缺点是通常太晚、太粗——对账 Agent 即使分类对了，也可能是绕了很大一圈才蒙对的。

**过程奖励**：是否调用了正确工具、是否遵守了执行顺序、是否读取了必要上下文、是否出现无意义重复查询。这类奖励能帮系统更快学到"怎样做更合理"，对应上一篇讲的行为层。

**成本奖励**：token 消耗、执行轮数、工具调用次数、总耗时。没有成本约束，系统很容易为了追求成功率而无限扩张步骤——多查两次总比查漏了安全，如果没人告诉它查询也有代价。

**安全与约束奖励**：有些行为即使结果正确也不该被鼓励，比如查询了超出权限的敏感字段、跳过了必要的复核步骤。这类行为通常需要单独的惩罚项,甚至是不可妥协的硬约束。

## 一个简单例子

继续用对账异常 Agent。一个初级的奖励函数可能是：

```text
分类正确 = +1
分类错误 = 0
```

这比没有目标强，但过于单薄。一个更合理的版本可能是：

```text
分类正确 = +1.0
判断依据可追溯 = +0.5
查询了超权限字段 = -1.0
重复无效查询 = -0.1
总步骤过多 = -0.2
```

这时系统优化的就不再是"想办法把分类蒙对"，而是更接近：判断正确、依据可查、少做越权和冗余的动作——这四个目标同时被塑造，而不是只有第一个。

## 多目标必须组合，不能只挑一个指标

真实目标通常不是单一指标。只奖励分类正确率，系统可能变得成本极高、过程冗长；只奖励低成本，系统又可能变得过于保守、遇到复杂差异就提前判给人工复核以规避风险。所以奖励设计通常不是"找一个最好的指标"，而是把多个目标组合成一个可优化的平衡结构。

## 代理指标与古德哈特定律

上一篇提到过古德哈特定律：一旦某个指标变成被优化的目标，它就不再是一个好的度量。奖励函数设计里最常见的翻车方式,正是用代理指标替代了真实目标——你真正想要的是"对账判断稳定可靠",但实际奖励的是"分类标签和历史数据对得上",系统就会越来越擅长拟合历史标签的表面模式,而不一定越来越擅长处理真正的新型差异。类似的错位还有把"响应速度快"当成"处理质量高",把"复核触发率低"当成"判断准确"。代理指标不是不能用,但必须清楚:它只是目标的近似,不是目标本身。

## 奖励黑客与委托-代理问题

一旦奖励定义得不够严谨,系统就可能学会"钻空子",这通常被称为 reward hacking。经济学里有一个对应的经典问题叫委托-代理问题(principal-agent problem):委托人(设计奖励的人)没法直接观察代理人(执行任务的系统)的真实行为,只能靠一些可观测的代理信号去考核,而代理人会精确地针对这些可观测信号去优化,即使这偏离了委托人的真实意图。

对账 Agent 如果奖励里只写了"复核触发率越低越好",它完全可能学会对疑难差异也强行给出一个"无需复核"的判断——因为这个信号只看触发率,看不到判断本身有没有依据。这不是系统"学坏了",而是它非常认真地执行了你写下的可观测指标。应对方式是持续追问:系统会不会利用这条规则走捷径,哪些看起来合理的奖励其实在诱导错误行为。

## 硬约束与奖励的边界

并不是所有要求都该写成奖励项。一个实用判断是:如果是"最好做到"的偏好,可以写进奖励;如果是"绝对不能违反"的规则,更适合写成硬约束。比如"尽量减少查询次数"适合做奖励,"不允许查询超出权限范围的敏感字段"更适合做硬约束——把绝对规则只写成惩罚项,惩罚力度不够大的时候,系统依然可能为了追求主目标而越界。

## 分层设计思路

实际工程里更稳的方式通常是分层:先用硬约束定义不可越界的边界,再用主奖励定义核心目标,最后用次级奖励调整效率、稳定性和过程质量。这比把所有东西都塞进一个大而混乱的分数公式更容易维护,也更容易在出问题时定位到是哪一层出了偏差。

一个简化的伪代码示例:

```python
def compute_reward(result):
    score = 0.0

    if result.classification_correct:
        score += 1.0

    if result.reasoning_traceable:
        score += 0.5

    score -= 0.05 * result.redundant_queries
    score -= 0.02 * result.total_steps

    if result.queried_unauthorized_field:
        return -1.0  # 硬约束：直接触发强惩罚，不参与其他项的加权

    return score
```

这里体现了三层逻辑:分类正确和依据可追溯是主奖励,冗余查询和步骤数是次级成本惩罚,越权查询是硬约束——一旦触发直接归零甚至倒扣,不和其他正向分数抵消。

## 五个自检问题

可以用下面几个问题快速检查一个奖励函数是否还算稳健:它是不是在逼系统优化你真正关心的目标?它会不会鼓励系统走捷径?它有没有明显忽视成本、稳定性或合规边界?多个目标之间有没有主次之分?当系统表现异常时,你能不能从奖励结构里看出原因?如果这几个问题里有两三个答不上来,通常说明这套奖励设计还很脆弱。

## 与 Eval 的关系

奖励函数和 Eval 很像,但方向不同:Eval 告诉你系统现在表现如何,Reward 告诉系统未来应该朝哪里进化。如果两者不对齐,就会出现训练时分数越来越高、但实际处理复杂差异的能力并没有变强的情况——这正是上一篇讨论的"结果偏见"在训练阶段的翻版:奖励只盯着结果层,系统就会在行为层和轨迹层上放飞自我。所以设计奖励时,最好始终回到 Eval 的四层框架(结果、行为、轨迹、系统)去对齐,而不是另起一套互不相干的评分逻辑。

## Harness 与 Skill 让奖励更复杂

一旦 Agent 不再是一次性完成任务,而是开始依赖 harness 提供的会话连续性和 skill 提供的流程模板,奖励信号就不能只盯着"最后结果是否成功",还需要考虑:harness 是否让系统更少中途丢失上下文、skill 是否真的提升了流程稳定性、是否因为调错了 skill 反而引入了额外的上下文噪声、是否为了追求长任务成功率而放任成本膨胀。系统能力层次越多,奖励函数越要提防局部优化把整体带偏。

## 本节总结

- 奖励函数定义的不是分数本身,而是系统长期的进化方向
- 单一奖励往往不够,真实目标通常需要多目标组合,并分成硬约束、主奖励、次级奖励三层
- 代理指标替代真实目标(对应古德哈特定律)和奖励黑客(对应委托-代理问题)是两个最常见的翻车原因
- 奖励设计应该始终回到 Eval 的四层框架去对齐,而不是另起一套评分逻辑
