# 客户访谈实战：找到一个值得解决的问题

你有一个 Agent 点子：让企业员工直接问 AI，就能查到内部知识、处理工单。下一步是写代码，还是先问几个人“你觉得这个产品怎么样”？这两种做法都有风险：前者可能做出没人急需的东西；后者往往只得到礼貌的鼓励。

更有效的起点是：**复盘对方最近一次真实工作**，而不是请对方预测自己将来会不会使用一个尚不存在的产品。本文以虚构的企业知识与工单助手为例，带你完成一次访谈和一张问题证据卡。例子中的人物、数字均为教学假设。

## 1. 先拆开四个容易混淆的人

| 角色 | 他们关心什么 | 你应该验证什么 |
| --- | --- | --- |
| 一线使用者 | 任务能否更快完成、答案是否可信 | 工作何时发生、现有办法和失败代价 |
| 团队负责人 | 处理效率、质量和人员负担 | 任务量、业务目标和风险容忍度 |
| 安全或 IT 负责人 | 权限、数据流、运维责任 | 什么数据可以接入、谁能批准 |
| 采购或预算负责人 | 价值、预算、合同和供应商风险 | 谁能决定试点、购买和续费 |

一个人可以兼任多个角色。使用者说喜欢产品，不等于组织有预算；领导说支持，也不等于一线会改变工作方式。

## 2. 访谈前，准备可被推翻的假设

用一句话写出：“当 **某类人** 遇到 **某个具体任务** 时，现在通过 **某种办法** 解决，导致 **可观察的代价**。”

> 教学假设：客服新人遇到退款规则问题时，需要搜索多个知识页面并询问同事；规则版本不一致导致确认耗时和返工。

再写反证：如果新人已经能迅速找到最新规则，或者问题主要是规则制定不清，那么知识助手未必是合适的解法。邀请不同经验水平的人，而不是只访谈熟人或最支持你的人。

## 3. 进行一次 25 分钟访谈

开场先说明目的、时间、是否记录和保密边界；不采集不必要的个人信息。对话顺序可以是：

1. **还原最近一次：** “最近一次处理退款规则问题是什么时候？从接到问题开始，你做了什么？”
2. **追踪实际动作：** “你先查了哪里？没找到之后怎么办？可以在不暴露敏感信息的前提下展示流程吗？”
3. **查找代价：** “哪一步最耽误时间？答错或找错版本会发生什么？多久出现一次？”
4. **理解替代方案：** “团队现在用什么办法？为什么没有完全解决？谁维护这些资料？”
5. **了解组织约束：** “如果要试新流程，谁需要参与？哪些资料不能进入外部系统？”
6. **确认下一步：** “我们能否在取得授权后，用几条脱敏案例一起验证流程？”

一线员工可能不知道采购流程；不要把“不知道”当成反对。遇到模糊回答，追问“上一次具体是什么情况”，并允许对方纠正你的理解。

### 把诱导问题改成事实问题

| 容易得到漂亮答案的问题 | 更有信息量的问题 |
| --- | --- |
| 你觉得 AI 助手很有用吧？ | 最近一次遇到这个问题，你怎么处理的？ |
| 你会不会每月付 999 元？ | 现在谁承担这个问题的成本？已经为哪些替代方案花过钱或时间？ |
| 我们自动解决所有工单怎么样？ | 哪些步骤你愿意让系统建议，哪些必须由人决定？ |
| 你每天都要查很多次吧？ | 过去一周你记得发生了几次？能否用记录核对？ |

如果最终需要测试价格，访谈过去的支出只能提供线索，不能代替具体报价、采购流程和付费行为。

### 创始人的做法：到问题发生的地方观察

Bump 联合创始人、后来负责 Google Photos 产品的 David Lieb 在 [YC 的访谈](https://www.ycombinator.com/blog/google-photos-product-lead-and-bump-cofounder-david-lieb-with-gustaf-alstromer/)中回顾，团队曾去人们自然社交的场景做用户测试，因为 Bump 的使用动作更可能在那里发生；他也提到早期亲自回复客户邮件，让自己持续接触用户的问题。这是他对自己经历的回忆，不是证明某一种访谈地点一定有效的实验。

把它迁移到企业 Agent 时，重点不是寻找同样的场所，而是观察**真实工作发生的时刻**。例如，征得同意后，请客服带你回看一张已经脱敏的工单：问题从哪里进入，员工在哪一步离开工单系统去查资料，谁决定是否升级。不要因为旁观不方便，就用“你平时应该会这样做”代替事实；也不要为了观察而要求对方暴露客户敏感信息。

观察之后，用三列记录：

| 观察或原话 | 可能的解释 | 下一次如何验证 |
| --- | --- | --- |
| 教学示例：员工查完文档又去问同事 | 文档可能不够可信，也可能只是习惯先确认 | 问清是否找不到、看不懂、版本不确定，或有强制复核要求 |

这个区分有实际后果：如果症结是**版本不可信**，优先修复来源维护与引用；如果是**必须复核**，就设计人审流程；如果只是搜索入口难找，未必需要 Agent。先用下一次观察区分假设，再决定做什么功能。

## 4. 把对话整理成证据，而不是结论

| 字段 | 教学示例 |
| --- | --- |
| 人与场景 | 客服新人处理退款政策咨询 |
| 原始观察 | 访谈对象表示上次先搜索文档，后询问资深同事；尚未核对工单记录 |
| 当前替代方案 | 搜索、群内提问、人工确认 |
| 代价假设 | 查询与等待耗时；需实际测量，暂不填写确定数值 |
| 约束 | 不得跨租户展示；规则版本需要可追溯 |
| 支持或反驳 | 是否存在最新权威来源？是否有人愿意提供脱敏任务参与测试？ |
| 下一步 | 找知识维护者确认来源，并观察 5 个授权任务的处理过程 |

把“受访者说”和“我们推断”分开写。单次访谈能提出假设，不能代表整个市场；关注重复出现的行为，也主动寻找相反的例子。判断是否继续时，综合问题频率、严重性、可触达性、组织约束和你能够交付的范围。

### 同一个问题，三个人可能给出不同答案

下面的对话是**虚构的练习**，不是客户访谈记录。假设创业者准备为客服团队做退款知识助手：

| 对象 | 虚构对话中的线索 | 不能直接推断什么 | 接下来验证 |
| --- | --- | --- | --- |
| 客服 | “上周有张工单，我找到两份规则，最后问了组长。” | 两份规则一定互相矛盾，或者等待一定很久 | 取得许可后回看脱敏工单，确认当时使用的文档版本和等待时间 |
| 知识维护人 | “其中一份其实是旧版，但还没下架。” | 做了检索界面就能解决维护流程 | 确认谁有权发布、撤回，旧链接和缓存如何处理 |
| 团队负责人 | “如果客服能更快答复值得试，但不能扩大退款权限。” | 负责人已经批准采购或允许连接生产数据 | 确认试点负责人、数据授权人、预算和采购流程 |

这三条线索改变的并不只是销售话术，也会改变工程方案：第一版先做**只读查询、来源版本展示与过期资料拒答**，而不是自动退款。Builder 要和资料维护人明确版本与撤回规则；Seller 要和负责人确认成功指标、参与者和采购路径。两者都应把“是否有人真的会用”和“资料能否安全提供”列为待验证条件。

如果维护人表示短期内无法确定权威版本，就应暂停把资料用于自动回答，先协助客户梳理来源。这个决定可能让演示变慢，却避免将一个资料治理问题包装成模型能力问题。

### 访谈结束前，约定一个可验证的下一步

不要把“听起来不错”记为成交信号。可以用下面的方式提出小而具体的请求，并明确对方可以拒绝：

> “我们想先验证客服能否更快找到可引用的现行规则。您是否愿意和资料维护人一起，选择几条可以授权使用的脱敏历史问题，约一次短会确认来源和试点边界？如果目前不方便，也请告诉我主要卡在哪一步。”

把结果分开记录：**同意讨论**、**愿意投入人员时间**、**允许使用具体数据**、**确认采购流程或签约**是不同的承诺，不能互相替代。记录下一步的负责人、需要取得的授权、约定时间及未确认事项；如果对方拒绝，也记录原因，不要自动解释成价格或技术问题。YC 的[企业商业模式指南](https://www.ycombinator.com/library/Gh-yc-guide-to-business-models)指出，企业销售通常涉及多个把关人和较长周期；具体流程仍要以客户组织为准。

## 5. 从访谈进入小型验证

不要把所有需求放进一个大产品。选定一个任务，例如“回答退款规则并附来源”，再列出最小验证：

- **基线：** 现有流程在一组真实、授权的任务上需要多久，错误如何被发现？
- **方案：** 用脱敏文档建立只读原型；没有证据就回答无法确认。
- **安全：** 没有获得身份与数据授权前，不接企业生产资料，不自动发送或写入。
- **结果：** 对比任务完成率、引用正确性、人工校正时间和用户是否愿意再次使用。
- **停止条件：** 如果来源本身不可靠或权限无法满足，就先解决数据问题，而不是增加 Agent 数量。

## 练习：写出你的第一张问题卡

选一个你能接触到的行业，访谈至少 3 种不同视角的人。每次结束后，用上表记录一条有出处的观察、一条推断、一条可能推翻推断的证据。数字只是练习规模，不构成统计代表性。访谈结束前不要推销，获得许可后再讨论下一步。

## 延伸阅读与观看

- [Y Combinator：How to Talk to Users（视频）](https://www.youtube.com/watch?v=MT4Ig2uqjTc)：重点看如何围绕过去行为而不是假设性赞美提问。
- [Paul Graham：Do Things that Don't Scale](https://paulgraham.com/ds.html)：理解为什么早期需要亲自寻找并服务用户；个案经验不等于所有行业都能复制。
- Rob Fitzpatrick，《The Mom Test》：读完后可用“这句话描述的是过去事实，还是对未来的礼貌预测？”检查自己的访谈记录。书中方法需要结合样本偏差和组织采购场景使用。
