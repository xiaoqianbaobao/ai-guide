# 从内容到第一个客户：建立可验证的增长闭环

写了一篇技术文章，有人点赞，却没有人来咨询；公众号有关注，读者却不知道你能帮他们解决什么问题。这不一定说明内容没有价值，也可能是读者从“认识你”走到“提出具体需求”的路径缺了一段。

这篇教程用一个**虚构的企业知识助手案例**说明：怎样让网站、公众号和客户访谈协同工作，同时避免把粉丝数直接当作收入。这里没有假定你已经有客户或公众号增长数据。

## 1. 先选一个具体读者与问题

“所有想用 AI 的企业”太宽泛，不足以决定写什么。假设你想服务中小企业中的客服或运营负责人，他们要回答一线同事的业务问题，希望降低找资料和确认版本的时间。

把目标写成一张假设卡：

| 项目 | 教学示例 |
| --- | --- |
| 读者 | 管理客服团队、对知识维护有责任的人 |
| 问题 | 一线人员查询规则慢，更新后仍沿用旧版本 |
| 当前替代方案 | 文档搜索、群里问人、人工抽查 |
| 可能的成果 | 更容易找到可追溯的规则；实际收益需要测量 |
| 我们能提供 | 公开教程、实操演示和可讨论的试点方法 |
| 反证 | 用户已有可靠检索入口，或问题根源在规则无人维护 |

真实选题前，阅读客户问题、与潜在读者交流；不要将这里的假设写成已验证市场。先读 [客户访谈实战](./customer-discovery)，再决定技术方案。

## 2. 让不同渠道各自承担一件事

| 触点 | 读者想解决的问题 | 建议提供 | 明确的下一步 |
| --- | --- | --- | --- |
| 公开网站 | 我如何系统学习和验证？ | 可搜索的教程、示例、源码、练习和来源 | 阅读下一章或实践 |
| 公众号 | 我如何持续获取你的研究视角？ | 有具体收获的文章、复盘和思考 | 自愿扫码关注 |
| 交流与访谈 | 这个问题在我的环境是否存在？ | 了解工作流程、约束与已有替代方案 | 在双方同意下约定交流 |
| 试点及服务 | 能否在受控范围内创造结果？ | 试点方案、验收、报价与责任边界 | 由双方决定是否合作 |

网站不应只提供空洞摘要再要求关注才能读正文。完整教程本身是信任基础；公众号可以承接更新与作者视角。付费课程、社群或服务尚未落实时，应标注规划，不展示不存在的名额、案例或承诺。

## 3. 把一个主题拆成一组有用的内容

以“企业知识助手如何避免跨租户泄露”为例：

1. **网站长文：** 从场景出发解释可信身份、权限过滤、引用、缓存与日志边界；提供可运行的简化代码和明确限制。参见 [知识助手第一刀](../agent/cases/knowledge-assistant-first-slice)。
2. **公众号文章：** 聚焦一个常见失误，例如“为什么只在提示词里写不能越权不够”，用一个简短示例解释原因，链接到网站完整教程。不是把同一篇文章简单截断。
3. **学习练习：** 让读者写出两个角色的权限表，并找出哪些测试可以发现越权。
4. **真实反馈：** 若读者主动讨论，询问现有工作流程、资料权限和最担心的失败。获得许可后记录，不主动收集客户机密。
5. **试点判断：** 如果有明确任务、授权样本和负责人，再讨论小范围试点；否则继续完善内容或访谈。

内容的共同主线是一项真实工作，不是每天追逐不同热点。参考 [YC 对早期用户和分发的讨论](https://www.ycombinator.com/library/dS-how-to-start-a-startup-building-product-talking-to-users-and-growing)，渠道效果会变化，需要观察和迭代，不能把某个渠道当成保证。

## 4. 度量路径，但先说清数据从哪里来

可以维护一张手工表格，每周记录：

| 阶段 | 指标例子 | 获取方式与限制 |
| --- | --- | --- |
| 到达 | 某篇文章的访问量 | 使用经适当配置的站点统计；访问量不是独立人数 |
| 有兴趣 | 文章内二维码图片被打开的次数 | 需要额外事件统计；打开不等于扫码 |
| 关注 | 公众号新增关注 | 以公众号后台口径为准，无法自动归因到每个网页 |
| 交流 | 用户主动提出与主题相关的问题 | 人工脱敏记录；不要无授权保存敏感对话 |
| 验证 | 双方同意的访谈或试点 | 记录范围、是否完成和下一步 |
| 成交 | 已确认付款的客户或合同 | 按实际合同与财务口径记录 |

**常见误判：** 页面访问减去公众号关注不能直接算转化率，因为两套数据的时间窗口、来源和去重口径不同。除非有经过同意、真实可用的渠道归因，否则应标为“来源未知”，不要声称扫码或付费来自某篇文章。

如果要引入统计，先明确目的、告知方式、数据保存时间与删除机制，再选择不收集不必要个人信息的方案；涉及身份、支付或用户数据时应单独设计服务端鉴权、备份与安全流程。

## 5. 一个四周实验（不是增长承诺）

- **第 1 周：** 完成一篇能独立解决问题的教程；找 3 位不同背景读者检查能否跟着操作。
- **第 2 周：** 写一篇公众号文章，解释教程中的一个取舍；对自愿给反馈的人问“哪里无法实践”。
- **第 3 周：** 找到可接触的目标用户，安排若干自愿访谈，记录相同问题是否反复出现及相反证据。
- **第 4 周：** 如果有明确负责人和授权数据，提出小范围试点；否则复盘选题、受众和问题，不制造成交故事。

每周记录投入时间、可验证的结果、读者反馈与下周调整。样本小的时候，这些数字用于学习，不用于宣称长期增长率。

## 6. 后端什么时候值得做

二维码、公开文章和学习路径可以由静态站点完成。只有当出现明确需求，例如**用户账号、购买权限、订阅管理、学习进度或经过同意的反馈收集**，才需要设计相应后端。先写清用户旅程和数据流，再确定存储、身份、权限、隐私告知、备份、费用和故障处理。付费功能还需选择真实可用的支付与交付方式，不应先放一个不能使用的购买按钮。

## 动手练习

选一篇现有教程，用一句话分别写出目标读者、具体问题、实践产出和自愿下一步。给两位读者看，问他们“读完后你会做什么”；若回答不清楚，就修改内容，而不是先增加营销按钮。接下来阅读 [从试点到第一个客户](./pilot-to-first-customer)。
