# Agent 产品如何证明价值：从功能交付到客户成效

<ArticleHeader module="产品与 FDE" :tags="['产品', '实战']" reading-time="18 分钟" prerequisite="了解 Agent 的基本能力；不要求产品管理经验" summary="从企业工单案例出发，把上线了什么、用户行为改变了什么、业务是否获益分开，并设计可以反驳自己的试点。" />

> 本文使用虚构企业和示意数据，数字不是实际客户结果。所提方案需要根据真实业务、安全要求与数据重新验证。

## 一、做完一个功能，客户就得到价值了吗？

一家虚构的设备服务公司每天处理客户报障。团队准备开发 Agent：读取工单、查产品手册、给客服提供处理建议。项目完成后，研发报告说：接入了三个工具，支持对话和知识检索，平均回答时间两秒。

这些信息有用，却不能单独回答负责人真正关心的问题：客户的问题是否更快解决？客服是否信任建议？错误建议有没有引入额外风险？处理一张工单的总成本是否下降？

[Martin Fowler 关于成效与产出的讨论](https://martinfowler.com/bliki/OutcomeOverOutput.html)指出，交付的功能数量并不等于它给使用者带来的改善。把这个思路放到 Agent 场景，可以分成三层：

| 层次 | 例子 | 容易遗漏什么 |
| --- | --- | --- |
| 产出 | 上线检索、引用和工单建议 | 功能存在并不意味着有人用、用得对 |
| 行为变化 | 客服在处理问题时查看并核验建议，减少重复查找 | 用户可能看了建议，却仍花更多时间确认 |
| 业务成效 | 正确解决问题的时间缩短，服务质量不下降 | 结果可能还受人员、工单类型和流程变化影响 |

这三层不需要只选择一层。功能是否正常、用户是否改变工作方式、业务结果是否改善，都需要观测；只是最终价值不能由功能数量替代。

## 二、先搞清楚：工单慢到底慢在哪里

客户说“希望做一个智能客服”，这是解决方案的表述，不一定是问题。FDE 或产品人员需要沿着一次工单走完整条链路：

1. 工单从哪里进入？哪些信息经常缺失？
2. 谁负责判断类别、查询资料、联系专家和最终回复？
3. 最耗时的是检索、等待专家，还是等待客户补充信息？
4. 一条错误建议可能造成什么损失？哪些操作必须由人确认？
5. 现有系统已经记录了什么，哪些数据可以在授权范围内使用？

假设访谈后发现，重复问题的主要耗时是查找版本匹配的手册，而复杂故障主要等待专家。这两类问题就不应该使用完全相同的方案：前者可以先做带引用的检索建议；后者可能更需要自动整理信息并转交专家。也可能进一步发现，慢的主要原因是手册多年未更新；这时首先修复知识来源，可能比增加一个 Agent 更有效。

### 把一句模糊需求改写成可验证假设

> 假设：针对指定的重复故障类型，客服能在工作界面中查看带版本引用的建议，将减少查找资料所需时间，同时不增加错误处理和升级率。

这不是已经成立的事实。它包含目标用户、任务范围、预期变化以及不能变坏的条件。接下来要通过观察和测试寻找支持或反驳它的证据。

## 三、指标不止一个：不要让优化变成刷分

| 指标类型 | 本案例中的候选指标 | 为什么需要 |
| --- | --- | --- |
| 主要结果 | 同类型工单从受理到正确解决的时间 | 直接关注用户问题是否被解决 |
| 用户行为 | 建议被查看、引用被打开、建议被修改或拒绝的比例 | 帮助理解功能有没有融入工作流 |
| 质量与风险 | 错误建议率、错误关闭后重开率、敏感信息越权率 | 防止只追求速度而损害质量和安全 |
| 成本 | 每张工单的模型、检索和人工核验成本 | 判断收益是否覆盖实际开销 |
| 覆盖范围 | 哪些类型的工单可用，哪些必须转人工 | 避免把局部成绩误说成适用于全部客户 |

指标定义必须具体。例如“解决时间”从客服首次接单还是客户提交时开始？等待客户提供信息算不算？“解决”以谁确认、是否重开为准？在试点前写下口径，避免看到结果之后临时更换标准。

## 四、用对照设计验证，而不是挑几次演示

下面是一套**示意试点**：

- 选择可以取得授权、适合辅助检索的一类工单；保留复杂或高风险工单的人工处理流程。
- 先记录一段时间的现有流程，明确工单数量、类型、耗时分布和返工情况。
- 条件允许时，在相似工单或团队之间设置试点组与对照组，并记录分配方式；如果无法随机分组，要说明差异及其对结论的影响。
- 试点组使用 Agent 建议，对照组使用原流程。两组都可以转人工，并采用一致的质量复核标准。
- 同时记录任务结果、用户行为、错误、人工核验时间和成本；定期抽样审阅失败案例。

假设试点组平均处理时间缩短，但它接到的工单本来更简单，就不能直接把差异归功于 Agent。应按工单类型、难度、客服经验等因素分层，检查样本是否足够，以及是否发生了其他流程变化。小样本的结果适合指导下一次实验，不代表已经证明大规模收益。

## 五、把“省了时间”算成可讨论的经济账

假设以下数字仅用于演示：每月 1,000 张适合试点的工单，每张平均减少 4 分钟人工查找，人工成本按每小时 120 元估算。

```text
理论节省时间 = 1,000 × 4 / 60 ≈ 66.7 小时 / 月
理论人工成本 = 66.7 × 120 ≈ 8,000 元 / 月
```

但这只是理论值。假设还需支付模型与检索 1,500 元、人工复核 2,000 元、系统运维 1,000 元，每月净收益估算约为 `8,000 - 1,500 - 2,000 - 1,000 = 3,500 元`，还没有计入前期实施费用、风险损失、税费和人员时间能否真正被释放。

更有用的做法是列出区间：如果工单覆盖率只有一半、核验耗时更高或者错误导致返工，结论是否仍成立？不要把“节省的分钟”直接等同于企业已经减少的工资支出；节省时间可能转化为更好的服务、处理更多工单，也可能暂时无法转化为财务收益。

## 六、交付时的三个关键边界

**对客户**：明确使用范围、已验证的数据、未覆盖场景和回退方式。演示中的虚构数据、实验结果与实际生产数据不能混用。

**对使用者**：让客服看到引用来源和不确定性，能修改或拒绝建议；不要为了提高采纳率隐藏错误或制造不必要的确认步骤。

**对企业系统**：模型提供建议不代表自动获得权限。用户身份、文档权限、外部写入与审批必须由可信服务端执行。具体实现可继续阅读 [Agent 安全边界](../02-agent-core/agent-security-boundaries)和[企业级 Agent 实战路线](../agent/cases/enterprise-agent-roadmap)。

## 七、练习：为一个试点写验收条件

你负责的企业希望 Agent 自动回答内部制度问题。请写出：

1. 一类明确的目标用户和一项具体任务；
2. 一条能够被数据反驳的价值假设；
3. 一项主要结果指标、两项质量或安全指标；
4. 一个证据不足时的预期行为，以及试点中止条件。

检查自己的答案：它是否只写了“上线问答功能”？指标是否有分母、时间范围和确认方式？如果回答快但引用错误，你的方案能否发现？

## 八、真实创业者谈产品：需求不是功能清单

在 Y Combinator 的《How to Start a Startup》课程中，Homejoy 联合创始人 Adora Cheung 回顾了与用户交流的经验：用户提出某个功能时，团队需要继续追问背后想解决的问题，而不是把每条建议都直接变成需求。她还建议先厘清产品解决的问题，并与潜在用户交流验证。可在 [YC 课程页面观看讲座并阅读文字记录](https://www.ycombinator.com/library/dS-how-to-start-a-startup-building-product-talking-to-users-and-growing)。

把这一经验用于上面的工单案例：当客户说“给客服加一个聊天机器人”时，别急着列聊天功能。可以请客服展示最近一次困难工单，问他们在哪里找资料、哪一步等待最久、最终如何确认答案；再和团队负责人确认处理质量及成本。一次访谈只能形成假设，还需要观察更多实际工单和不同角色的反例。

这是一位创业者在特定业务阶段的经验，不是已证明对所有企业客户都有效的规律。企业采购者、实际使用者和安全审批方可能不是同一个人，需要分别了解。

## 延伸资源：看什么，怎么用

- **文章／核心概念**：[Martin Fowler：Outcome Over Output](https://martinfowler.com/bliki/OutcomeOverOutput.html)。先区分交付物与客户成效，再注意文中讨论的归因难题；练习时为同一功能各写一个产出指标和一个结果指标。
- **系统课程／视频与文字记录**：[YC／斯坦福创业课程：Building Product, Talking to Users, and Growing](https://www.ycombinator.com/library/dS-how-to-start-a-startup-building-product-talking-to-users-and-growing)。重点看问题定义和访谈；观看后用一页纸记录目标用户、最近一次问题和当前替代方案。讲座来自消费服务创业场景，迁移到企业采购时需要补充多角色、安全和集成约束。
- **创始人访谈**：[YC：Google Photos 产品负责人、Bump 联合创始人 David Lieb 访谈](https://www.ycombinator.com/blog/google-photos-product-lead-and-bump-cofounder-david-lieb-with-gustaf-alstromer/)。关注团队如何接触用户；读完设计一次不带推销目标的工作现场观察。
- **书籍**：[Marty Cagan，《Inspired》，第二版](https://www.oreilly.com/library/view/inspired-2nd-edition/9781119387503/)。公开目录与介绍显示其重点包括产品团队、产品发现和交付；可对照自己的团队检查谁负责验证价值、可行性与可用性。页面可能需要订阅；这里基于公开介绍给出阅读方向，不冒充全书读后评述。
- **书籍／客户开发**：[Steve Blank 的 Customer Discovery 介绍](https://steveblank.com/2010/08/26/) 与《The Four Steps to the Epiphany》。从客户发现和商业模式假设入手，读时记录哪些问题适用于企业客户、哪些需要按当前环境调整；这里是阅读指引，完整书评待通读后补充。
