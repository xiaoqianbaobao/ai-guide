## 一个需要先纠正的前提

之前把 Claude Code 和 Codex 归为“CLI 型 harness”，这个判断在几个月前是准确的，但已经过时了。现在两者都有独立的桌面应用：Claude Code 的桌面端支持并行管理多个会话、可视化 diff 审查、GitHub PR 监控；Codex 的桌面端也支持多任务并行、PR 审查、以及计算机操作能力，并且在最近的一次更新里，直接并入了 ChatGPT 的统一桌面应用，和 Chat、Work 模式并列。

也就是说，两家现在都提供了：CLI、桌面应用、IDE 插件、云端/远程任务这几乎一样的四种接入方式，而且背后是同一套执行引擎。比如 Claude Code 官方文档明确写了 CLI 和桌面端“共享同一个引擎”，项目记忆、权限规则、MCP 配置、Skill 都是同一份，区别只是“你用哪个界面驱动它”。

这个事实，比“哪种界面更好用”更值得深挖。

## Harness 商品化，指的是什么

商品化（commoditization）在产品和商业策略里，指的是一类曾经能构成差异化优势的能力，随着行业里大家都跟进复制，逐渐变成“不具备就出局，具备了也不加分”的标配。云计算的基础算力、浏览器的标准渲染能力，都经历过这个过程。

Harness 现在正在经历同样的事情。半年前，“能不能有一个稳定的长任务循环”“能不能有项目级的记忆文件”“能不能安全地在沙箱里执行命令”，这些还是能构成产品差异的能力；现在这些已经变成两家都必须具备的基础设施：项目记忆文件（`CLAUDE.md` 对 `AGENTS.md`）、权限审批模型、沙箱执行、Skill/Plugin 扩展、MCP 协议支持、多会话并行管理、PR 审查集成。这份清单两边都在对齐，几乎变成了“编码 Agent 产品”的标准配置表，而不是某一家的独门武器。

## 表层证据：界面清单正在趋同

把两者现在提供的入口列出来看会很直观：

| 接入方式 | Claude Code | Codex |
| --- | --- | --- |
| 命令行 | 有 | 有 |
| 独立桌面应用 | 有，支持并行会话、可视化 diff | 有，现已并入 ChatGPT 统一桌面应用 |
| IDE 插件 | VS Code、JetBrains | 有对应 IDE 集成 |
| 云端/远程任务 | 有（Routines、Dispatch） | 有（Codex Cloud、云端任务） |
| 项目级指令文件 | `CLAUDE.md` | `AGENTS.md` |
| 移动端触发 | 支持从手机远程唤起桌面任务 | 支持语音、跨端协同 |

这张表如果放在一年前，任何一行都可能是某一家的核心卖点；现在放在一起看，几乎每一行都是“两家都有”。这正是商品化最直观的表现，当你发现自己在用“有没有某个能力”来做选型依据时，往往说明这个能力已经不再是有效的选型依据了，因为两边都有。

## 但要小心：界面趋同不等于内核趋同

这里有一个容易被误判的地方，值得先泼一盆冷水：**清单趋同，不代表实际能力趋同。**

两家都有“沙箱执行”，不代表两家的沙箱在权限颗粒度、危险操作拦截的准确率上是一回事；两家都有“项目记忆文件”，不代表两家在超长项目、规则冲突时的处理方式一样扎实；两家都支持“并行会话管理”，不代表两家在多会话之间共享上下文、避免相互干扰的工程实现处于同一水平。

表层清单的趋同，很大程度上是“竞品对齐”的结果。一旦一家推出了某个能力，另一家几乎必然会在几个月内跟进，不然会被视为“缺功能”。但跟进出一个功能，和把这个功能做到同样成熟，是两件事。所以商品化目前更准确的说法是：**入口和功能清单层面的商品化，先于底层执行质量的商品化。** 后者能不能真的追平，需要更长时间和更细致的实测才能判断，不能因为清单看起来一样，就假设体验也一样。

## 商品化之后，差异化去了哪里

如果 harness 的入口清单已经不再是有效的比较维度，真正值得关心的问题是：这两家现在到底在往哪个方向差异化竞争。从两边最近的动作里，能看出两条不同的路径。

### 路径一：Claude Code 往“编排”方向走

Claude Code 桌面端的改版，被外部评价为“从对话转向编排”的哲学转变。重点不再是和一个 Agent 对话，而是同时管理多个正在运行的会话，在它们跑偏时介入，在完成时审查。配合 Routines 这类自动化能力，Claude Code 的差异化叙事正在从“这一次任务完成得好不好”，转向“我能不能同时协调很多个任务，把自己从执行者变成调度者”。

### 路径二：Codex 往“统一工作台”方向走

Codex 选择并入 ChatGPT 统一桌面应用，和 Chat、Work 模式并列，而不是继续作为一个独立的“程序员专用工具”存在。这意味着 OpenAI 的差异化押注，不是把编码体验做得比对手更专精，而是把编码能力揉进一个更广的“全能工作助手”故事里。你打开的不是一个编码工具，而是一个顺带能编码的通用助手。

这两条路径背后是完全不同的产品哲学：一个赌“专业开发者需要更强的多任务编排能力”，一个赌“编码能力应该被收编进更大的通用助手叙事里”。**这才是 harness 入口清单趋同之后，真正还没有被磨平的分歧点。** 不在“能不能做某件事”，而在“整个产品往哪个方向长”。

## 一个值得追问的反面问题

前面的论证有一个隐含假设：harness 商品化之后，差异化一定会转移到别处。这个假设本身也值得被追问。**会不会存在一种可能，harness 层的竞争根本没有结束，只是转移到了更难被外部观察到的细节里？**

比如，两家在“上下文压缩策略”上的具体算法、在“多会话并行时如何避免上下文串扰”上的工程实现、在“沙箱逃逸防护”上的安全边界，这些差异外部用户很难直接感知，但每天都在真实使用体验里发挥作用。如果真是这样，那“harness 已经商品化”这个判断，可能只是“harness 的表层商品化了，但深层还在激烈竞争，只是竞争战场从用户能看见的功能清单，转移到了用户看不见的工程细节”。这和“harness 不再重要了”是完全不同的结论。

这也提醒一个更普遍的教训：**当一层能力开始出现“清单趋同”时，不要急着下结论说这层不再重要了，更值得做的是去问：这层里还有哪些维度没有被清单化、没办法靠一句“支持不支持”来比较。** 往往正是这些没被清单化的维度，才是接下来几个版本真正决出高下的地方。

## 对于实际选型意味着什么

如果你现在要在 Claude Code 和 Codex 之间选，这个视角给出的建议是：

- 不要再用“这个有没有桌面端”“那个支不支持云端任务”这类问题做决策依据，这些现在基本都是标配，问不出有效信息
- 更值得问的是“我更需要多任务编排能力，还是更希望编码能力嵌在一个更广的工作助手里”，这对应两家现在真正分化的战略方向
- 如果条件允许，用真实项目实测同一类任务在两边的执行稳定性和上下文处理质量，而不是对照功能列表，这是清单商品化之后，唯一还没被磨平的比较维度

## 本节总结

- Claude Code 和 Codex 现在都提供 CLI、桌面端、IDE 插件、云端任务这几乎一样的接入方式，背后是同一套核心引擎，说明 harness 曾经的差异化能力正在变成两家都要具备的标配
- 表层的界面和功能清单趋同，不等于底层执行质量趋同，这是判断商品化程度时最容易被误判的地方
- 差异化正在从“有没有某个入口”转移到“整个产品往哪个方向长”，Claude Code 押注多任务编排，Codex 押注融入更广的通用工作助手
- 值得警惕的反面观点是：harness 层的竞争可能没有消失，只是转移到了用户难以直接观察的工程细节里，清单趋同不代表竞争结束
