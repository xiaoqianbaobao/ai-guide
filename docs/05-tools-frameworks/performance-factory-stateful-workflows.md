# 从告警到恢复：把长任务做成可交接的 Agent 工作流

凌晨出现一次性能告警。Agent 查了指标、找到可疑提交，并写出修复建议；可是代码审查和部署要等白天。如果它的全部进展只保存在一次对话里，下一位接手的人如何知道当前在哪一步、证据是什么、还需要谁批准？

这正是长任务与单次对话的区别：工作需要**跨进程、跨人、跨事件保存状态**。2026 年 11 月 19 日，OpenAI 介绍了用于处理性能回归的 [Performance Factory](https://openai.com/index/how-openai-performance-factory-keeps-chatgpt-fast/)。本文先拆解其公开架构，再用一个独立的 Python 状态机演示关键设计；示例并非 OpenAI 内部代码。

## 1. 先分清自动调查和闭环

OpenAI 描述的演进路径从人工调查开始：工程师先借助 Agent 分析，再把重复的调查方法沉淀成可复用技能；之后告警可以自动触发调查，但修复与部署仍需接力。最终，工作流将调查、提出修复、等待人审核和部署、验证恢复组织成一个持续任务。

据其文章，系统主要由任务服务、调度循环、云端 Agent 执行环境和事件订阅组成。任务保存状态与发现，调度器找出可以继续的工作，订阅在审查或部署发生变化后唤醒任务。工程师仍负责审查并决定发布什么；部署后还需要确认指标是否恢复，而不是把“提交了修复”当作问题已解决。

OpenAI 报告了内部使用数据，但这是其特定团队和系统的自报结果，不能直接推算你自己的成功率或收益。本篇更关注可迁移的机制及其适用边界。

## 2. 把自然语言工作变成明确状态

下面是教学用简化模型：

| 状态 | 谁推动下一步 | 需要留下什么 | 不能假设什么 |
| --- | --- | --- | --- |
| 调查中 | Agent 或工程师 | 告警、观察窗口、证据和未证实假设 | 相关性一定是根因 |
| 等待审查 | 有权限的审查人 | 修复方案、风险、回滚方法 | 提交补丁等于批准 |
| 等待部署 | 发布流程 | 已审查版本、发布结果、环境 | 批准等于已上线 |
| 验证恢复 | Agent 或工程师 | 修复后指标、对照基线、观察窗口 | 发布后指标必然恢复 |
| 已解决 | 系统记录结论 | 可追溯的验证证据 | 一次恢复证明永不复发 |

验证发现问题仍存在时，任务应回到调查；缺少权限或证据时，需要记录阻塞原因并交给合适的人，而非生成确定结论。不同企业可以采用不同状态，不必照搬这张表。

## 3. 运行一个小状态机

在仓库根目录使用 Python 3.10+ 执行，代码全部离线，不连接模型、告警系统或生产服务：

```bash
cd examples/regression-workflow
python3 workflow.py
python3 -m unittest -v
```

演示依次进入等待审查、等待部署、验证，最后因为指标仍未恢复返回调查；测试覆盖不能跳过审查、重复事件、事件 ID 冲突、恢复失败和恢复成功。完整代码与测试在 [regression-workflow](https://github.com/xiaoqianbaobao/ai-guide/tree/main/examples/regression-workflow)。

关键部分是事件必须匹配当前状态：

```python
next_state = TRANSITIONS.get((self.state, event))
if next_state is None:
    raise ValueError(f"event {event!r} is invalid in {self.state!r}")
self.state = next_state
```

状态机只约束流程，**不会自动验证事件真假**。真实系统中，`review_approved` 必须来自可信审查服务并验证审批人与修复版本；`deployment_finished` 必须验证来源和部署目标。不能让 Agent 发送一个字符串，就宣称人已经批准。

## 4. 为什么等事件，而不是让模型一直运行

代码审查可能要几小时，部署也可能排队。持续占用一个模型会话无法保证更好的恢复：进程可能退出、上下文可能过期，还会浪费资源。更可靠的设计是保存任务，暂停执行，收到相应事件后重新调度。

一次可交接记录至少应包含任务 ID、状态与版本、关联事件、可访问的证据链接、已经尝试的方法、已知结论与不确定性、待执行操作及责任人。证据记录与推测分开；如果监控数据会过期，还应在授权范围内保存可复核的快照或查询条件。

示例的 `seen_events` 只在进程内去重，进程退出就丢失。生产实现需要持久化事件和状态，使用事务或可靠消息机制处理并发、重复投递、顺序颠倒与崩溃恢复；外部副作用仍要结合目标系统的幂等与对账能力。参考 [工单审批、幂等与恢复](../agent/cases/ticket-approval-and-retry)。

## 5. 评估调查和交接，要分开看

原文介绍，OpenAI 使用历史事故回放测试调查过程，并避免让测试者看到事故复盘或先前运行结果等可能泄露答案的信息；它还单独评估任务摘要能否让不熟悉系统的工程师理解证据与下一步。这里有两个可迁移的问题：

1. **调查正确吗？** 告警开始时间、受影响请求、候选原因和证据是否一致？哪些结论仍不确定？
2. **接手的人能行动吗？** 是否能找到原始图表、了解证据支持的范围，知道下一步由谁做？

历史数据可能已经过期，复盘材料可能泄露答案，指标恢复也可能碰巧与部署同时发生。应记录评估时可见的数据、时间窗口和评分方式；对高风险场景，保留人工复核。不要只用摘要是否流畅打分，也不要把一次根因判断正确当作稳定可靠。

## 6. 从练习到真实系统

1. 给 `Task` 增加 `version`，构造两个执行者同时尝试推进同一版本的场景，设计冲突检测。
2. 为人工审批事件增加关联修复版本；版本变化后，验证旧审批不能继续推进。
3. 把任务状态与事件放进持久存储，在写入任一部分时模拟崩溃，明确恢复时应重放还是人工处理。
4. 定义一张任务交接卡：事实、假设、证据、权限不足和下一步分别是什么？让没有参与调查的人检查是否可接手。
5. 先在脱敏历史事件上回放，单独测根因判断和交接质量，再决定是否连接真实告警。
